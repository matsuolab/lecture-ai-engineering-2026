## 宿題

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  `app/config.py` の `RAG_TOP_K` を 5 から 2 に変更した（21行目、1行のみ）。
  変更前後で、同じ質問を `uv run python -m app.agent --trace` で実行して比べた。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？
  - モデル：gemini-3.5-flash-lite
  - 対象資料：第1〜3回の本講義（ベクトル検索の範囲）
  - 検索ツール：`search_materials` のみ（ベクトル検索）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

  | 項目 | TOP_K=5（変更前） | TOP_K=2（変更後） |
  |---|---|---|
  | 検索語 | LoRA 固定 学習 QLoRA 加える | LoRA QLoRA 固定 学習 第2回 |
  | ツール呼び出し | search_materials 1回 | search_materials 1回 |
  | 回答 | 正答 | 正答 |
  | 引用 | 第2回 p.52, p.51 | 第2回 p.52 |
  | 時間 | 3.12秒 | 4.38秒 |
  | 入力／出力 tokens | 3,028／192 | 1,531／173 |
  | モデル応答回数 | 2回 | 2回 |
  | 推定費用 | $0.001388 | $0.000892 |

  変更前後とも、LoRAは元の重みを固定して低ランク行列 A・B だけを学習し、QLoRAは元の重みの4bit圧縮を加える、と答えられた。
- 改善した例と、残る失敗・制約：
  - 改善：入力トークンが約49%、推定費用が約36%減った。この質問は p.52 だけで根拠がそろうため、回答は正答のままだった。
  - 残る点：TOP_K=5 の回答にあった「さらに少ないメモリで調整できる」という補足（根拠は p.51）が、TOP_K=2 では回答から消えた。
  - 制約：1回ずつの計測であること。検索語がエージェントによって毎回変わるため、件数だけの比較にはなっていない。
- 気づき・疑問：
  - 件数を減らすと、負担は減る一方で補足的な根拠が落ちる可能性がある。この質問のように1ページで答えが決まる場合は、少ない件数でも十分だった。
  - 時間は入力が減ったのに1.26秒増えた。原因がAPIの応答のばらつきなのかは、1回ずつの計測では分からない。
  - 疑問：複数ページにまたがる質問（例：コンパクションとセッションをまたぐメモリの違い）では、TOP_K=2 で根拠が足りなくなるのではないか。
