## 宿題

- 取り組んだレベル：実装（検索ヒットの前後1ページも取得する改良。比較条件として検索件数も変えた）

### やったこと（変更したファイル・設定・処理）

- `app/retrieval.py`：`add_neighbors` と `search_with_neighbors` を追加。検索ヒットの前後 N ページ（N=1）の本文を付けて返す。
  - 同じ資料の中だけで隣を取る（別資料はまたがない）。
  - 同じページは1回だけ（ヒット同士が隣り合う場合はヒット側を残す）。
  - 各結果に `role`（`hit` か `neighbor`）と、どのヒットの隣か（`near`）を付ける。
- `app/config.py`：環境変数で切り替えられるようにした。`AIE_NEIGHBORS`（前後に足すページ数。既定0＝従来どおり）、`AIE_TOP_K`（検索件数。既定5）。
- `app/tools.py`：`search_materials` が `search_with_neighbors` を使う。エージェントがモデルへ実際に渡したページを `[retrieved] 3-p26, 3-p27*, …`（`*`は前後ページ）として標準エラーに出す。`--trace` では本文が見えないため。
- `lectures/05/neighbor_check.py`：検索結果だけで、答えのページが「前後なし」「前後あり」で入るかを比べる（LLM は使わない）。
- `lectures/05/run_matrix.py`：質問・検索件数・前後の有無を変えて `app.agent --trace` を自動で繰り返し、時間・トークン・費用・取得ページ・引用ページを記録する。
- 実装と集計スクリプトの作成には Claude Code を使った。実行と結果の確認は自分で行った。

### 改善した例と、残る失敗・制約

- 改善した例：HITL（二重注文・二重送金の説明が、前後なし0/4→前後あり4/4）、QLoRA（p.53 の引用が 1/4→4/4）。いずれも、前後なしでは k=2,3 のどちらでも答えのページが取れなかった。
- 不要な情報が増えた例：HITL k=3・前後あり（2回目）は、2回目の検索で第3回の無関係な章を含む16ページが入り、入力が 11,244 tokens になった（同じ k=3・前後なしの2回目は 2,904 tokens）。

- 効果がなかった例：事後学習は答えのページ（p.25）が前後なしでも取れており、前後ありでも回答の質は変わらなかった。
- 制約：各条件は2回ずつで、差は傾向として読む。最初の30回のうち16回が失敗し（確認できた原因は API のレート制限と混雑(503)）、待ち時間と再試行を足して実行し直した。回答の正誤は、回答本文を読んで自分で判定した。

### 気づき・疑問

- 最初に作った5問は、質問文に答えのページの語（「JSON」「送金や注文」「料金」など）を入れてしまい、5問とも前後なしで答えのページが入った（前後ページの効果が見えなかった）。答えのページの語を質問に入れすぎないほうが、効果を測れる。
- エージェントは質問を言い換えて検索する。質問文そのままで検索した結果（`neighbor_check.py`）では HITL の p.27 は3位で入るが、エージェント実行の前後なし（k=3、2回）では入らなかった。検索だけの確認は、実行結果の代わりにならない。
- 集計の「必要ページ」に、質問の主題のページ（A）まで入れていたため、引用率が実際より低く出た。答えが書かれたページだけに直した。
- `--trace` はツールの返却本文を途中で切るため、取れたのに使われなかったのか、取れなかったのかが区別できなかった。`[retrieved]` を足して区別できるようにした。
- 疑問：前後ありでは、QLoRA と事後学習の検索回数が毎回1回だった（計8回）。前後なしは、事後学習が毎回2回、QLoRA が1〜3回（平均2.0回）。HITL は前後の有無で平均1.5回のまま変わらなかった。この違いの理由は確かめていない。
- Graph の取得処理を `app/retrieval.py` と `data/rag_data/graph.json` で調べた（Graph のエージェント実行はしていない）。
  - ページ同士の線は `next_page`（前後）だけで、`mentions`（用語の出現）はページと用語をつなぐ線。そのため、1 hop で取れるページは前後ページだけになる。宿題で実装した前後1ページは、Graph の1 hop の部分にあたる。
  - Graph は検索上位3ページを入口に2 hop まで広げ、入口を含め10ページを返す。
  - エージェントが実際に取った入口ページを使い、`search_graph` と同じ手順を `graph.json` で計算した。QLoRA（入口 p.52, 54, 60）の返却に p.53、HITL（入口 p.26, 25, 48）の返却に p.27、事後学習（入口 p.24, 23, 25）の返却に p.25 が入った。
  - 用語を経由する線では、複数ページの質問（入口 p.39, 65, 38）の p.13 は2 hop（p.39 →「メモリ」→ p.13）で候補に入るが、候補100ページのうち14位で、返却の上位7ページ（上限10−入口3）に入らなかった。「メモリ」は17ページにつながっており、つながりが多い用語は優先度が下がる。事後学習の計算では、用語経由で質問と関係のない第1回 p.4・p.7（「システムプロンプト」経由）が入った。
- 疑問：返却上限（`GRAPH_MAX_RESULTS`）や優先度を変えると、p.13 のような隣り合わないページに届くか。そのとき入力トークンはいくつ増えるか。発展として確かめたい。
- 疑問：演習の Graph（4.32秒・ツール呼び出し1回）が少ない手順で済んだのは、`--graph` モードがモデルに `search_graph` 1つだけを渡すため（通常モードは5つ）でもある。Graph の仕組みの効果とツール数の違いを、分けて比べたい。
