### やったこと（変更したファイル・設定・処理）

**基礎：`RAG_TOP_K` を 5 → 10 に変える（1か所だけ）**

- `app/config.py` の `RAG_TOP_K` を環境変数 `AIE_RAG_TOP_K` で上書きできるようにした（既定は 5 のまま）。`AIE_RAG_TOP_K=10 uv run python -m app.agent --trace "…"` で変更後を試せる
- 指示文・ツールの説明・ツール名は変えていない

**実装：検索結果に前後1ページの本文を付ける（`--neighbors`）**

- `app/retrieval.py` に `add_neighbor_pages(hits, pages, window=1)` と `search_with_neighbors(query)` を追加
  - 前後は **同じ資料（`document_id`）の中だけ** で探す。第1回の最終ページの「次」に第2回の p.1 を付けない
  - **同じページは1回だけ** 返す。上位のページが別の hit の前後としても出るときは `role: "hit"`（距離・順位付き）として扱う
  - 並びは検索順位を保ち、各 hit ごとに「前 → hit → 後」。前後で足したページは `role: "neighbor"`・`neighbor_of`（どの hit の前後か）を持つ
- `app/tools.py` に `search_materials_with_neighbors` を追加。`app/agent.py` ではこれを **ツール名 `search_materials` のまま** 登録し（`NEIGHBOR_TOOL`）、`--neighbors` で切り替える。INSTRUCTIONS は通常の検索と同じ。説明文には「role が hit / neighbor の意味」の1行だけを足した
- `--trace` の `search_materials` の戻り値を「`7ページ・本文3,305文字: 第2回 p.51（前後）、第2回 p.52 …`」の形で表示するようにした（モデルへの入力は変わらない）
- `uv run python -m app.retrieval --neighbors "LoRA QLoRA 違い"` で、検索だけの結果も前後付きで確認できる
- テスト：`tests/test_neighbors.py`（資料をまたがない・重複しない・hit を優先・資料の端・window=0、ツール名が同じまま結果がモデルに届くこと）、`tests/test_lec05_homework_script.py`（比較スクリプトを API なしで最後まで通す）。`uv run pytest -q` で全件 pass

### 改善した例と、残る失敗・制約

**根拠が増えた例（q5）**：前後付きでは、クイズ3（p.42・43）の前の p.41「決まった判断は『小さな分類モデル＋プログラム』で、速く安く」と、後の p.44「モデル選びの手順（自分の評価セットで精度・料金・待ち時間を測る）」が入り、理由を p.41・43・44 の3ページで裏付けた。通常 top5 は問題と答えのページ（p.42・43）だけを根拠にしていた。

**不要な情報が増えた例**：
- q3（資料にない質問）：上位5件がどれも関係の薄いページなので、その前後も関係がなく、15ページ・8,852字に膨らんだ。入力は 3,201 → 7,255 tokens（2.3倍）で、回答は変わらない
- q1：p.52 の前後（p.51・53）は関連するが、演習ページ p.60・61 の前後としてまとめ（p.59）や次回予告（p.62）、p.47 の前後として p.46・48 も入った

**残る失敗・制約**：
- 今回の5問では、**通常の top5 だけで根拠を全部取れていた**（7/7）。スライドは隣のページ同士が似た内容なので、ベクトル検索が前後のページをもともと一緒に拾っていた（q2 の p.39・40、q4 の p.61・62、q5 の p.42・43）。前後ページの取得で初めて取れた根拠はなかった
- 基礎（top10）も根拠は増えず、入力だけが増えた。今回の質問では top5 で足りていた
- エージェントの比較では、検索語をモデルが毎回作るので、方式間で検索語が少し違う（q1 は「…第2回」と「…追加」）。この揺れを除くため、検索だけの比較は検索語を固定した
- 先に前後として入ったページが、あとで検索にも当たると「hit」に上がるが、並び順は前後として入った位置のまま（q1 で p.51 が p.52 より前に来た）

### 気づき・疑問

- 「前後を付ける」はページを増やすだけなので、関係のない hit が多い質問ほど損をする。全部の hit に付けるより、1位だけ、距離が閾値より近い hit だけ、または本文に「次のページ」「（答え）」のような続きの手がかりがある hit だけに絞るほうが、この資料には合いそう
- 根拠の取得・引用の数だけ見ると3方式は同点で、違いは入力トークンと費用だけだった。質問の作り方（根拠がたまたま隣同士で上位に入る質問）によって、改善の効果が見えなくなることがある。前後ページが本当に要るのは「本文が短く、検索語と重ならない続きのページ」で、そういう質問を評価セットに入れないと差は測れない
- 疑問：スライドの「4/4 選んだモデルを…」のような共通の見出しが埋め込みの文章に入っていることで、同じ章のページ同士が似たベクトルになっている可能性がある。見出しを除いて索引を作ると、検索結果がどう変わるか
