  資料をすべて渡すよりも、必要な部分だけを検索して渡した方が効率よく回答できる場合があると分かった。Treeは正確なページを取得できたが、探索回数が多く時間もかかった。Graphも正答できたが、今回の質問では基本RAGより多くのトークンを使用した。複数の章にまたがる質問では、どの方式が有利になるのか気になった。

## 宿題

- **取り組んだレベル：** 基礎

- **やったこと（変更したファイル・設定・処理、または設計した取得方法）：**

  `app/config.py`の`RAG_TOP_K`を5から1に変更した。検索件数を減らすことで、必要な情報を維持したまま入力トークン数やAPI費用を削減できるかを検証した。

- **比較した質問と、固定した条件（モデル・対象資料など）：**

  質問は演習と同じ「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」を使用した。モデルはgemini-3.5-flash-lite、対象資料は第1〜3回の本講義資料とし、検索件数のみを変更した。

- **結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：**

  | 項目 | 変更前（5件） | 変更後（1件） |
  |---|---|---|
  | 回答 | 正答 | 正答 |
  | 引用根拠 | 第2回 p.51、52 | 第2回 p.52 |
  | 時間 | 2.41秒 | 3.25秒 |
  | 入力トークン | 3028 | 1189 |
  | 出力トークン | 151 | 194 |
  | モデル応答回数 | 2回 | 2回 |
  | 生成API推定費用 | $0.001286 | $0.000842 |
  | ツール呼び出し | 1回 | 1回 |

  変更後も`search_materials`が1回呼び出され、p.52を取得して正しく回答できた。入力トークン数は約60.7%、生成API推定費用は約34.5%削減できた。一方、回答時間は2.41秒から3.25秒に増加した。

- **改善した例と、残る失敗・制約：**

  今回はp.52だけで必要な情報がそろっていたため、検索件数を1件に減らしても正答でき、トークン数と費用を削減できた。ただし、複数ページに根拠が分かれている質問では、検索件数を減らすことで情報が不足する可能性がある。また、今回は回答時間の短縮は確認できず、試行回数も少ないため、性能の変化を一般化することは難しい。

- **気づき・疑問：**

  検索件数を増やせば必ず回答が良くなるわけではなく、必要な情報が含まれているかが重要だと感じた。単純な質問では検索件数を減らすことで費用を抑えられるが、複雑な質問では複数のページが必要になる可能性がある。質問の難しさに応じて検索件数を自動調整できれば、さらに効率的になるのではないかと考えた。
