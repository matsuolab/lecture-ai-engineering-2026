- 検索だけを実行して見つかったページと、その本文で確認できたこと：`uv run python -m app.retrieval "LoRA QLoRA 違い"` で5件取得し、1件目が第2回・PDF p.52「LoRA と QLoRA：大きなモデルも GPU 1 台で調整できる」で、元の重みは固定し小さな差分（行列A・B）だけを学習すること、QLoRAでは元の重みを4bitに圧縮することが本文で確認できた。2件目のp.51（PEFT）も補足の根拠になる。
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：ベクトル検索は search_materials を1回（query: 'LoRA QLoRA 固定 学習 第2回'）。Treeは browse_tree を4回（ルート→lec02-main→章「選んだモデルを、いつ・どう直すか」→p.52の本文取得）。Graphは search_graph を1回（入口は lec02-main-p052）。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：全文投入は根拠ページ（p.51・52）を含む全資料を渡したのに、QLoRAの4bitを明示せず曖昧な回答になった。「取得できたのに回答へ使えなかった」例にあたる。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：ベクトル検索。入力トークンが最も少なく費用も最安で、根拠ページを正確に引用できた。ただし比較した質問は1つだけなので、質問によって結果は変わりうる。
- 気づき・疑問：全文投入は速いが入力トークンが桁違いに多く（117,025）、答えも曖昧だった。検索で絞る方が安く正確だった。

## 宿題

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K`（ベクトル検索で返す件数）を 5 から 2 に変更し、同じ質問を `--trace` 付きで実行して変更前後を比べた。
- 比較した質問と、固定した条件（モデル・対象資料など）：質問は演習と同じLoRA/QLoRAの質問。モデル（gemini-3.5-flash-lite）と対象資料は変更前と同じ。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：変更前（5件）は入力3,037トークン・3.08秒・$0.001444、変更後（2件）は入力1,740トークン・2.87秒・$0.000977。回答は変更後も正しく、引用もp.52・p.51で変わらなかった。ツール呼び出しは search_materials 1回で同じ。
- 改善した例と、残る失敗・制約：根拠ページが検索上位にある質問では、件数を減らしても回答の質を保ったまま入力トークンと費用を約4割減らせた。ただし根拠が上位に来ない質問では、件数を減らすと根拠を取りこぼす可能性がある。
- 気づき・疑問：検索件数は多いほど良いわけではなく、根拠ページの順位しだいで最適な件数が変わると感じた。
