## 宿題

- 取り組んだレベル：発展
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/graph2.py`：観点ごとに入口を作る Graph 検索 `search_graph2(queries)` を新規作成
  - `app/tools.py`：ツール `search_graph2` を追加
  - `app/agent.py`：`--graph2` モードを追加（指示文は Graph 用を流用し、観点の分け方を1行追加）
  - `scripts/compare_graph.py`：旧 Graph と graph2 の取得ページを LLM なしで比べるスクリプト
  - 設計：

    | | 旧 Graph | graph2 |
    |---|---|---|
    | 入口 | 質問全体で1回検索し、上位3件 | 観点ごと（最大3つ）に検索し、各2件。観点はモデルが `queries` で指定 |
    | 広げ方 | 前後ページとすべての用語を最大2 hop | 入口の前後ページ ＋ 質問語に一致する用語ノードのページだけ |
    | 並べ方 | hop数 → 接続の少ない用語を優先 | どれかの観点との埋め込み距離が近い順（DBのページ埋め込みを再利用） |
    | 上限 | 10ページ | 10ページ（同じ） |

  - 選んだ理由：比較の質問では両方の観点の根拠が必要だが、1回の検索では片方に寄った入口しか取れない。また旧 Graph は接続の少ない用語を優先するため、「メモリ」のような中心的な用語のページ（p.13）が後回しになり枠からこぼれていた。件数は増やさず、同じ10ページの中身を入れ替えることを狙った

- 改善した例と、残る失敗・制約：
  - 改善：必要3ページの取得が 2/3 → 3/3 になった。用語「メモリ」経由で、別の章にある p.13 を拾えた。1回目の回答は p.13 を引用し、旧 Graph より説明が厚くなった。入力は旧 Graph より少ない（5,282 → 4,577 / 3,898）。モデルは説明文の例を写さずに、自分で観点を分けた
  - 悪化なし：対照の LoRA の質問は正答のまま。資料にない質問では数字を作らなかった
  - 残る失敗：p.40 は graph2 で取得できていても、検索系のどの方式の回答でも一度も引用されなかった（引用したのは全文投入だけ）。取得を改善しても「使われる」ことまでは保証できない
  - 残る失敗：2回目は p.13 の内容を使ったのに引用していない。観点の分け方（2つ／3つ）も実行ごとに変わり、結果が安定しない
  - 制約：「メモリ」のような一般的な語では関係の薄いページ（p.50, p.4）も入る。観点の数だけ埋め込みAPIを呼ぶので時間が延びやすい（35.55秒の回もあった）。ただし測定中に503が出るほど混雑しており、時間の差は誤差が大きい。各条件1〜2回の試行なので優劣は断定しない
  - 採用するか：比較・章をまたぐ質問では採用したい（取得の網羅性が上がり、費用は旧 Graph と同程度で、全文投入の約1/15〜1/18）。単一ページの質問や資料にない質問では利点がなく、ベクトル検索のほうが速く安い。質問の種類で経路を切り替えるのがよい
- 気づき・疑問：
  - 「取れた」と「使われた」は別物だった（講義第4章「入ることと使われることは別」）。旧 Graph も p.40 を取得していたのに使わなかった。検索結果と最終回答は分けて評価する必要がある
  - 次に直すなら「使われない・引用されない」側。返却結果を観点ごとにまとめて渡す、回答前に各観点の根拠ページを引用したかを確かめる仕組みを入れる、など（講義第6章：検証は指示ではなく仕組みに組み込む）
  - Tree は本文を読んでいない p.41 を引用していた。候補一覧の先頭文だけで引用してしまう点は、引用の妥当性を自動で確かめたくなる例だった
