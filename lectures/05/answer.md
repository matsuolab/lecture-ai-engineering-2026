### 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例

今回の質問では、基本RAG・Tree・Graphのいずれも必要な根拠を取得でき、内容に大きな誤りは見られなかった。

一方、全文投入では関連ページを示すことはできたものの、具体的な答えを直接提示せず、ヒント形式の回答となった。資料不足ではなく、エージェントの指示や回答生成時の情報利用が影響した可能性がある。

また、Treeではp.52だけで回答できたものの、該当ページに到達するまで4回のツール呼び出しを必要とした。

### 今回の用途に採用したい方式と、その理由・比較条件の限界

今回のように、講義資料の特定の概念について質問する用途では、**基本RAG（ベクトル検索）を採用したい**。

全文投入と比較して、基本RAGでは入力トークン数が117,025から3,028へ約97.4%減少し、推定生成API費用も約69.4%削減された。回答の内容と引用根拠も適切であった。

TreeとGraphでも正しい回答が得られたが、今回の質問では基本RAGに対する明確な品質向上は確認できなかった。

ただし、全文投入と検索方式では対象資料が異なる。また、各方式1回ずつの測定であるため、処理時間や回答品質について一般的な優劣を判断することはできない。

### 気づき・疑問

- 大量の資料をモデルに渡すことと、必要な根拠を実際に回答へ利用できることは別である。
- 検索によって入力トークン数と費用を削減できるが、検索処理やツール呼び出しによって時間が増加する場合もある。
- Treeは探索経路が明確である一方、階層をたどるために複数回のツール呼び出しが必要となった。
- Graphは関連情報の探索に有用と考えられるが、今回の質問では追加の効果を明確に確認できなかった。
- 検索方式を公平に比較するには、対象資料を統一し、複数の質問と繰り返し測定によって評価する必要がある。

### やったこと

`app/config.py`の検索件数を設定する`RAG_TOP_K`を変更した。

変更前：

```python
RAG_TOP_K = 5
```

変更後：

```python
RAG_TOP_K = 3
```

検索件数以外の設定は変更せず、同じ質問で回答・根拠・処理時間・トークン数・推定API費用を比較した。

### 比較した質問と固定した条件

**質問**

「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」

**固定した条件**

- モデル：`gemini-3.5-flash-lite`
- 検索方式：基本RAG（ベクトル検索）
- 対象資料：第1〜3回の本講義資料
- 質問文：同一
- 実行コマンド：`uv run python -m app.agent --trace "第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？"`

### 結果

|---|---:|---:|

**主な変化**

- 入力トークン数：949トークン削減（約31.3%減）

変更前後とも`search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})`が1回呼び出され、検索結果の先頭として`lec02-main-p052`が表示された。

### 改善した例と、残る失敗・制約

今回の質問では、検索件数を5件から3件に減らしても、LoRA・QLoRAの説明と引用根拠を維持できた。必要な情報が少数の検索結果に含まれている場合、検索件数の削減によってトークン数と費用を抑えられることが確認できた。

一方、検索件数を減らすと、複数ページに分散した情報を必要とする質問で根拠を取りこぼす可能性がある。

また、処理時間は短縮されず、3.23秒から3.40秒に増加した。各条件1回のみの測定であり、この差が検索件数の変更によるものか、実行時の変動によるものかは判断できない。

### 気づき・疑問

今回の実験を通して、RAGの検索件数は多ければよいわけではなく、**回答に必要な根拠を維持しながら、入力トークン数や費用を最適化することが重要**だと学んだ。

今後は、単一ページで答えられる質問だけでなく、複数ページや章を横断する質問も用いて、Top-Kを変えたときの正答率・根拠の取得率・費用を比較したい。また、処理時間については複数回測定し、実行時のばらつきも考慮したい。
