- - 取り組んだレベル：基礎

- やったこと：
  app/config.py の RAG_TOP_K を5から2に変更した。
  検索するページ数を減らすことで、回答の正確さや
  処理時間、トークン数、API費用がどう変わるか比較した。

- 比較した質問：
  第2回の説明では、LoRAは何を固定し何を学習しますか？
  QLoRAは何を加えますか？

- 固定した条件：
  モデルは gemini-3.5-flash-lite を使用。
  質問文、対象資料、その他の設定は変更しなかった。

- 結果：

  | 項目 | 変更前（5件） | 変更後（2件） |
  |---|---|---|
  | 回答 | 正解 | 正解 |
  | 引用根拠 | 第2回 p.51、52 | 第2回 p.51、52 |
  | 処理時間 | 3.33秒 | 3.00秒 |
  | 入力トークン | 3,028 | 1,741 |
  | 出力トークン | 221 | 174 |
  | モデル応答回数 | 2回 | 2回 |
  | 生成API推定費用 | $0.001461 | $0.000957 |

- --trace で確認したこと：
  変更前後とも search_materials が呼び出された。
  LoRAは元のモデルの重みを固定し、小さな追加行列を
  学習すること、QLoRAはさらに元の重みを4bitに
  量子化することを正しく回答できていた。
  引用根拠も第2回のPDF p.51、52で一致していた。

- 改善した例と残る失敗・制約：
  検索件数を5件から2件に減らしても、
  今回の質問では必要な根拠を取得できた。
  入力トークン数は約42.5%、生成API推定費用は
  約34.5%減少し、処理時間も0.33秒短縮した。

  ただし、複数ページに根拠が分散している質問では、
  検索件数を減らすことで必要な情報を
  見落とす可能性がある。

- 気づき・疑問：
  RAGでは検索する情報を増やせば必ず回答が
  改善するわけではないことを実感した。
  必要な根拠を確保できれば、検索件数を減らすことで
  トークン数や費用を削減できると分かった。

  今回は各条件を1回ずつ実行した結果なので、
  今後は質問の種類を変えたり、複数回実行したりして、
  検索件数と回答精度の関係を確認したい。
