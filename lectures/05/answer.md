<!-- 基礎・実装・発展のどれか1つに取り組めば完了です。 -->

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：app/config.py の RAG_TOP_K を 5 から 3 に変更した。ベクトル検索で取得する資料の件数を減らし、回答と根拠、ツール呼び出し、実行時間、トークン数、推定費用を比較した。
- 比較した質問と、固定した条件（モデル・対象資料など）：質問は「LoRAとQLoRAの違いは何ですか？」とした。モデルは両方とも gemini-3.5-flash-lite を使用し、第1〜3回の講義資料を対象に、同じ --trace オプションで実行した。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

  | 項目 | 変更前（TOP_K=5） | 変更後（TOP_K=3） |
  |---|---|---|
  | 回答の要点 | LoRAは低ランク行列による差分を学習し、QLoRAは元の重みを4bitに量子化する | 同じ内容を説明できた |
  | 引用した根拠 | 第2回・PDF p.51、p.52 | 第2回・PDF p.51、p.52 |
  | ツール呼び出し | `search_materials({'query': 'LoRA QLoRA 違い'})` を1回 | 同じツールを同じ引数で1回 |
  | 実行時間 | 2.71秒 | 6.61秒 |
  | 入力トークン数 | 2,995 | 2,047 |
  | 出力トークン数 | 171 | 165 |
  | モデル応答回数 | 2回 | 2回 |
  | 生成API推定費用 | $0.001326 | $0.001027 |

- 改善した例と、残る失敗・制約：TOP_Kを5から3に減らしても、今回の質問では回答の主要な内容と引用ページを維持できた。入力トークン数は948減少し、生成API推定費用も約23％減少した。一方、実行時間は2.71秒から6.61秒に増加した。これはモデルや通信の状態などにも左右されるため、TOP_K変更が原因とは断定できない。また、検索件数を減らすと、質問によっては必要な根拠を取りこぼす可能性がある。
- 気づき・疑問：取得する資料を多くすれば必ず回答がよくなるわけではないと分かった。今回のように少ない検索件数でも十分な根拠が得られる場合は、トークン数や費用を抑えられる可能性がある。ただし、1つの質問を各条件で1回ずつ比較した結果なので、今後は複数の質問や繰り返し実行で確かめたい。
