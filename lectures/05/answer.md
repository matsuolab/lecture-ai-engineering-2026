# 第5回 解答

## 演習
回答モデル（実行時の [model]）：gemini-3.5-flash-lite

比較した質問： 「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」

対象資料： 第1〜3回の講義資料。全文投入では資料全体を入力し、ベクトル検索・Tree・Graphでは検索方法によって取得範囲が異なる。

### 各方式の結果

| 方式 | 回答の要点・正しさ | 引用ページと根拠 | 時間（秒） | 入力/出力トークン数 | モデル応答回数 | 生成API推定費用（USD） |
|---|---|---|---:|---:|---:|---:|
| 全文投入 | 正答。LoRAは元の重みを固定して差分を学習し、QLoRAは元の重みを4bitに圧縮する | 第2回 PDF p.51, p.52 | 2.21 | 117,025 / 212 | 1 | $0.004681 |
| ベクトル検索 | 正答。必要な情報を検索して回答できた | 第2回 PDF p.51, p.52 | 3.46 | 3,028 / 170 | 2 | $0.001333 |
| Tree | 正答。階層をたどって必要な情報に到達した | 第2回 PDF p.51, p.52 | 6.72 | 9,214 / 330 | 5 | $0.003589 |
| Graph | 正答。関連ページをたどって必要な情報を取得した | 第2回 PDF p.51, p.52 | 3.24 | 5,771 / 221 | 2 | $0.001736 |

検索だけを実行して見つかったページと、その本文で確認できたこと： uv run python -m app.retrieval "LoRA QLoRA 違い" を実行し、5件の検索結果を確認した。 LoRA・QLoRA・Fine-Tuningなど意味的に関連するページが取得された。 一方で、QLoRAという語を含んでいても今回の質問への直接の根拠ではないページも含まれており、意味的に近いページが必ずしも回答に必要なページとは限らないことを確認した。
--trace で見えたツール呼び出し： ベクトル検索では search_materials が呼び出され、質問に関連するページを検索していた。 Treeでは browse_tree を複数回呼び出し、講義→章→ページという階層をたどって目的の情報を取得していた。 Graphでは search_graph が呼び出され、質問に近いページを起点として関連するページを取得していた。

取得した情報が足りなかった例、取得できたのに回答へ使えなかった例： 今回の質問では必要なp.51、p.52を取得できたため、回答に必要な情報が不足するケースは確認できなかった。 ただし検索単体では、質問と関連する語を含むものの、直接の回答には不要なページも検索結果に含まれた。このため検索件数を増やすことが必ずしも回答品質の向上につながるとは限らないと考えた。

今回の用途に採用したい方式と、その理由・比較条件の限界： 今回の質問ではベクトル検索を採用したい。 全文投入と比較して入力トークン数を117,025から3,028へ大幅に削減しながら、同じp.51、p.52を根拠として正答でき、推定費用も$0.004681から$0.001333へ削減できた。 TreeやGraphも正答したが、今回の質問ではベクトル検索より入力トークン数や推定費用が大きかった。 ただし、これは1つの質問による比較であり、資料の構造やページ間の関係を利用する必要がある質問ではTreeやGraphが有利になる可能性がある。

気づき・疑問： LLMに多くの情報を与えればよいわけではなく、質問に必要な情報を適切に選んで渡すことが重要だと分かった。 全文投入は今回もっとも短時間だったが、入力トークン数と費用が大きかった。一方、ベクトル検索は検索処理が追加されるものの、必要な情報に絞ることでトークン数と費用を大幅に削減できた。 TreeやGraphには構造や関連性を利用できる特徴があるため、質問の種類によって検索方法を使い分ける必要があると感じた。

## 宿題
取り組んだレベル：発展
やったこと（変更したファイル・設定・処理、または設計した取得方法）： app/config.py の GRAPH_HOPS を 2 から 1 に変更し、Graph検索の探索範囲を2 hopから1 hopに制限した。 必要な根拠を維持しながら、取得する情報量・トークン数・コストを削減できるか検証した。

比較した質問と、固定した条件（モデル・対象資料など）： モデルは gemini-3.5-flash-lite、対象資料は同じ講義資料に固定した。 以下の2つの質問で GRAPH_HOPS=2 と GRAPH_HOPS=1 を比較した。

「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」
「Fine-Tuningが向いているケースと、RAGが向いているケースの違いを説明してください」
結果（変更前後の回答・根拠、--trace の出力、時間・トークン数・生成API推定費用など）：

質問1：LoRA / QLoRA
条件	入力tokens	出力tokens	時間	推定費用	結果
GRAPH_HOPS=2	5,771	221	3.24秒	$0.001736	正答
GRAPH_HOPS=1	4,020	195	3.22秒	$0.001694	正答
どちらも第2回 PDF p.51、p.52を根拠として、LoRAは元の重みを固定して差分を学習し、QLoRAはさらに元の重みを4bitに圧縮することを回答できた。 HOPSを1に減らすことで、回答品質を維持したまま入力トークン数を約30%削減できた。

質問2：Fine-Tuning / RAG
条件	入力tokens	出力tokens	時間	推定費用	結果
GRAPH_HOPS=2	5,119	496	3.51秒	$0.002776	正答
GRAPH_HOPS=1	3,499	609	4.17秒	$0.002572	正答
どちらもFine-Tuningはモデルの「振る舞い」を変えたい場合、RAGは新しい事実や最新情報などの「知識」を与えたい場合に向いていることを回答できた。 HOPS=1でもp.46、p.47、p.57、p.58などの必要な情報を取得でき、入力トークン数は約32%減少した。

改善した例と、残る失敗・制約： 今回試した2つの質問では、2 hopから1 hopに探索範囲を狭めても回答品質を維持しながら入力トークン数と推定費用を削減できた。 一方で処理時間は必ずしも短縮されず、質問2ではHOPS=1の方が時間がかかった。 また、今回の質問では1 hop以内に必要な情報が存在したが、離れたノードの情報を必要とする質問では、HOPS=1では必要な情報を取得できない可能性がある。

気づき・疑問： Graph検索では探索範囲を広げれば常に良いわけではなく、必要以上に探索するとコンテキスト量やコストが増えることが分かった。 今回の2問ではGRAPH_HOPS=1の方が効率的だったため、この条件では1 hopを採用したい。 ただし質問によって必要な探索範囲は異なるため、複数種類の質問で評価してHOPSを決めることが重要だと感じた。
