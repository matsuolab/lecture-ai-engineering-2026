- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K` を変更し（既定値から `7` に増やし、その後 `3` に減らして比較）、同じ質問を `--trace` 付きで実行した。
- 比較した質問と、固定した条件（モデル・対象資料など）：質問「第2回の説明では、LoRAは何を固定し何を学習しますか? QLoRAは何を加えますか?」、モデル `gemini-3.5-flash-lite`、通常ベクトル検索（第1〜3回本講義・214ページ）。
- 結果（変更前後の回答・根拠、`--trace` の出力、時間・トークン数・生成API推定費用など）：
  - `RAG_TOP_K = 7`（`search_materials`）：2.83 秒 / 入力 4,006・出力 175 tokens / モデル応答 2 回 / 推定コスト $0.001639 USD（第2回・p.52 `lec02-main-p052` を取得し正答）
  - `RAG_TOP_K = 3`（`search_materials`）：3.21 秒 / 入力 2,077・出力 178 tokens / モデル応答 2 回 / 推定コスト $0.001068 USD（第2回・p.52 `lec02-main-p052` を取得し正答）
- 改善した例と、残る失敗・制約：件数を `3` に減らしても必要な根拠ページを取得でき、入力トークンと推定コストを抑えられた。一方で、件数を絞りすぎると必要な根拠が漏れるリスクがあり、増やしすぎると入力トークンやコストが増え、ノイズも混ざりやすくなる制約がある。
- 気づき・疑問：`top-K` を増やすと幅広く根拠を探せる反面、トークン数やコストが上がり、不要な情報が増えることで精度に影響する可能性もあるため、必要な根拠がそろう範囲で絞るバランスが重要だと感じた。
