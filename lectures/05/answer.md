- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

    - トークン数: 入力 **2,079 tokens**（**約31%削減！**） / 出力 183 tokens

- 改善した例と、残る失敗・制約：
  - **改善した点**: 質問への回答に必要な核心情報（p.51, p.52）は検索上位1〜2件に含まれていたため、件数を5から3に絞っても回答精度を全く落とすことなく、余分なスライド（p.60演習以降）のコンテキストを削って入力トークン数を約1,000トークン（約31%）大幅に削減できた。
  - **残る制約・失敗**: 単一トピックの質問では3件で十分だったが、複数講義にまたがる複雑な質問や、関連用語が広範に散らばっている質問の場合、`TOP_K=3` では重要な根拠が足切りされて回答精度が低下するトレードオフがある。
- 気づき・疑問（調べてみたこと・考察）：
  - **件数削減（TOP_K=3）の効果**:
    - 「とりあえず多めに取得する（TOP_Kを大きくする）」とコンテキスト長とAPIコストが無駄に増大するため、質問の性質やチャンク粒度に合わせて適切なTOP_Kをチューニングすることの重要性を数値（約31%削減）で実感できた。
  - **失敗リスクと実務での調整方法（調べてみたこと）**:
    - `TOP_K` を削りすぎると、複数トピックにまたがる質問などで必要なスライドが足切りされ、回答精度が落ちるリスクがある。
    - 実務では「勘」で決めるのではなく、第4回で扱ったような評価セット（50〜100問の典型質問）を用意し、`TOP_K` を変えながら正答率とコストの推移を測定して、最も費用対効果が高いスイートスポットをデータで定量決定するのが王道であることを学んだ。
  - **情報取得に失敗した際の実践的対策（調べてみたこと）**:
    1. **リランキング（Reranking）**: まずベクトル検索で粗く多め（例: 20件）に取得し、軽量なリランカーモデルで厳選して上位数件に絞ってからLLMに渡す（取りこぼし防止とトークン節約の両立）。
    2. **エージェントによる自己反省・自律再検索（Corrective RAG）**: 回答に必要な根拠が足りない場合、LLMが別キーワードで再検索を行うループ構造を持たせる。
    3. **ハイブリッド検索**: 意味で探すベクトル検索と、型番・固有名詞に強いキーワード完全一致検索（BM25）を併用する。
    4. **ガードレール**: 情報不足時にハルシネーションを起こさないよう、「資料からは確認できませんでした」と正直に答えさせる制約をプロンプトで徹底する。
