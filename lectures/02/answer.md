## 宿題

### 1. 取り組んだレベルと変更点

**レベル: 基礎**

`CONFIG` の `num_train_epochs` を **20 → 40** に変更した。それ以外は既定のまま
（`lora_r`=16、`lora_alpha`=32、`lr`=2e-4、`warmup_steps`=6、`seed`=42、`gen.do_sample`=False、
`base_model`=Qwen/Qwen3.5-0.8B、`revision`=2fc0636…、バッチ 4 × 勾配累積 2）。

手順は、20 エポックのまま一度最後まで実行して `result.json` を退避し、
**ランタイム → セッションを再起動**してから 40 エポックに変えて、セクション 0 から実行し直した。
学習前の評価も毎回そのセッションで取り直している。両実行の学習前スコアが完全に一致していることが、
条件が揃っていることの確認になる（下表の「学習前」列）。

| 条件 | 20 エポック（基準） | 40 エポック（変更後） |
|---|---|---|
| ステップ数 | 40（1 エポック 2 ステップ） | 80 |
| 学習するパラメータ | 6,389,760 / 758,782,784 = **0.8421%** | 同左（`lora_r` は変えていない） |
| 学習率・warmup | 2e-4 / 6 ステップ（cosine） | 同左 |

- 知識を問う質問（4 問）の分類は、20ep と 40ep で**1 問も変わらなかった**

### 3. 観察（数字から言えること）

**① 形式は学習で変わり、学習量を増やしても伸びない。**
学習前の形式違反 19 問は、すべて `missing_key`（JSON としては読めるが `needs_review` が無い）。
プロンプトで「必ず `answer` と `needs_review` を返す」と指示してあるのに守れていない。
残る 2 問は形式は通ったが `{"answer": "否", "needs_review": false}` と中身が誤り。
20 エポックの LoRA で 2/21 → 21/21 になり、40 エポックでも 1.000 のまま。
**天井に達しているので、学習量を倍にしても形式は改善しない**（伸びしろがない）。

**② 内容は形式ほど伸びず、学習量を倍にすると 1 問減った。**
0/21 → 19/21 まで上がったが、40 エポックでは 18/21。
21 問の評価なので **1 問 = 4.8 ポイント**。1 問分の差は、seed を固定しても GPU 上の学習が
完全には再現しないことを踏まえると、**改善でも悪化でもなく「差がない」と読むのが妥当**。
学習量を倍にした効果は、今回のデータでは観測できなかった。

**③ loss は下がったが、精度は上がらなかった。**
最終 loss は 0.0138 → 0.0109（−21%）と下がり、学習時間は 242 → 498 秒（ステップ数にほぼ比例）。
しかし `content_rate` は 19/21 → 18/21 で、**loss の低下はタスクの正解率の向上を意味しない**。
教師データ（14 件）への当てはまりが良くなっただけで、言い換えへの般化は良くなっていない。

**④ 残った失敗は「FAQ の別項目を流用して断定する」型に集中している。**
40 エポックでは、`成績はいつ出ますか` と `課題の文字数に制限はありますか` の**2 問が同じ「提出形式」の文**を返した。
別項目への流用がむしろ強まっている。

| 質問（FAQ に無い） | 20ep 学習後 | 40ep 学習後 |
|---|---|---|
| 成績はいつ出ますか | 提出期限を流用して断定（`needs_review: false`） | 提出形式を流用して断定 |
| 課題の文字数に制限はありますか | ○「記載がありません。確認が必要です」 | **提出形式を流用して断定（新たに失敗）** |
| オフィスアワーは事前予約が必要ですか | オフィスアワーを流用して断定 | 同左 |

学習後の回答は、多くの場合 FAQ の原文をそのまま返す形になっている。
**文面は教師データに揃うが、「FAQ に根拠があるか」の判断は揃っていない**ことが、この 3 問に出ている。

**⑤ 知識を問う質問では、1 問だけ断定が残った（前後・エポック数とも同じ）。**

| 質問 | 学習前 | 学習後 |
|---|---|---|
| この講座の最終課題の締切はいつですか | `format_error` | `asserted`（提出期限を流用して断定） |
| 担当教員の名前は何ですか | `format_error` | `needs_review` |
| 次回の講義のテーマは何ですか | `format_error` | `needs_review` |
| 課題の提出期限はいつですか（対照） | `format_error` | `asserted`（正しい断定） |

3 問中 2 問は「確認が必要」に変わったが、最終課題の締切は**別項目の流用で断定**したまま。
ここでも、**形式が整うことと、根拠の有無を判断できることは別**だと分かる。

> 補足: 4 行目（対照質問）はノートブック上で「FAQ にある: false」と表示されるが、
> これは `gold` が test の質問だけを持つためで、実際は FAQ に根拠がある質問。
> したがって `asserted`（`needs_review: false`）は**誤りではなく正しい断定**。

**⑥ 退行が 0 件なのは「安全だった」という意味ではない。**
`regressed` は「学習前は形式も内容も通っていたのに学習後に落ちた質問」の定義。
今回は学習前の `both_rate` が 0.000（通った質問が 0 件）なので、**定義上、退行は検出できない**。
この 0 件は「退行しなかった」証拠にはならない。

### 4. 考察

**ファインチューニングが向く場面**
- 出力の**形式・スキーマ・文体**を揃えたいとき。今回はプロンプトで指示しても 2/21 しか守れなかったものが、
  14 件・4 分の学習で 21/21 になった。ルールをプロンプトで書き切るより、例で示すほうが効く類のタスク。
- 判断の揺れを減らし、毎回同じ形で返させたいとき（後処理やパースが前提のシステム）。

**向かない場面**
- **知識の更新**。FAQ に無いことを聞かれても「確認が必要」と返せるようにはならず、
  別項目を流用して断定する失敗が残った。社内固有の最新情報や頻繁に変わる事実を覚えさせる用途には向かない。
  検索して Context に入れる構成（第 3 回）のほうが適切。
- **根拠の有無の判断**。`needs_review` はデータ設計（根拠なし例をどう混ぜるか）に依存し、
  学習量を倍にしても改善しなかった。ここは学習ではなく、検証・しきい値・人のレビューで担保する領域。

**学習量について**
`num_train_epochs` を 20 → 40 にすると、loss は下がり学習時間は 2 倍になったが、
形式は天井、内容は 1 問減った。
14 件を 40 周（各例 40 回）すると教師文の丸暗記が強まり、言い換えへの般化が落ちる可能性は考えられるが、
**1 問差なので断定はしない**。確かめるなら seed を変えて複数回試す必要がある（今回は時間の都合で各 1 回）。

**この実験の限界**
- test は 21 問なので、分解能は 1 問 = 4.8 ポイント。1〜2 問の差は結論に使えない。
- 各条件 1 回のみ。seed 固定でも GPU 学習は完全再現しない。
- 評価は貪欲生成（`do_sample: False`）なので、サンプリングした場合の挙動は別。
