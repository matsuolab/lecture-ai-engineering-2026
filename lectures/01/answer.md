## 宿題

- 取り組んだレベル：実装
- 使ったモデル：gemini-3.5-flash-lite（既定）
- やったこと：
  - `app/ask.py` に `--chat` オプションを追加し、会話履歴を保ったまま続けて質問できるようにした
  - `client.chats.create()` でチャットセッションを作り、`send_message()` を繰り返し呼ぶ。セッションが質問と回答を履歴として持ち、毎回まとめて送る
  - `exit` で終了し、終了時に履歴のメッセージ数を表示する。APIエラー（レート制限など）が出ても会話は続き、失敗したターンは履歴に残らないので同じ質問をやり直せる
  - 手順6のトークン数表示を `print_usage()` にまとめ、会話モードでも毎ターン表示する
  - `tests/test_ask.py` を追加した。偽のモデルを使い、APIキーなしで「2回目の呼び出しに1回目の質問と回答が含まれる」ことを確かめる
- 実行方法：`uv run python -m app.ask --chat "LoRAとは何ですか？"`
- 結果：
  - `uv run pytest -q`：13 passed
  - 1ターン目「LoRAとは何ですか？」→ LoRA（Low-Rank Adaptation）の仕組みとメリットを長く説明（input=7, output=617）
  - 2ターン目「それを一言で言うと？」→「AIの頭脳をごっそり改造せず、小さなお手伝いファイル（付箋）を追加して、手軽に自分好みにカスタマイズする技術」と、「それ」を LoRA と解釈して答えた（input=633, output=41）
  - 終了時の履歴のメッセージ数：4（質問2・回答2）
- 気づき・疑問：
  - 2ターン目の入力トークン数（633）は、1ターン目の入力（7）＋出力（617）＋新しい質問の分とほぼ一致した。会話履歴はサーバー側に保存されるのではなく、毎回すべて送り直していることが数字で確認できた
  - そのため、会話が長くなるほど1回あたりの入力トークンが増え、コストやレート制限に効いてくる。特に1ターン目のように回答が長いと、以降のすべてのターンが重くなる
  - 疑問：長い会話では、古い履歴を要約したり捨てたりする必要がありそう。どこで区切るのがよいか
