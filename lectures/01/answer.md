# 第1回 解答

## 演習

- 講座に固有の質問（宿題の3レベル）へのモデルの回答（要約でよい）：
  素のLLM（gemini-3.5-flash-lite）は「AIE2026」という講座を知らないため、「アクセス権限がないので断定できない」と前置きした上で、一般的な研修・教育プログラムでよくある「3レベル」の例（難易度別、ブルームのタキソノミー、DX人材のステップなど）を3パターン推測して提示してきた。断りを入れつつも、もっともらしい解説をかなりの分量で生成した。
- 用語集の正しい意味と比べて気づいたこと：
  `data/glossary.json` の `homework-levels` によると、正解は「基礎（講義内容の確認）」「実装（自分でコードを書く）」「発展（調査や試行）」の3段階で、どれか1つに取り組めば完了、というシンプルな話だった。モデルの回答は分量も説得力もあるが、中身は完全に的外れ。知らないことに対して「わかりません」で止まらず、もっともらしい一般論を自信ありげに組み立ててくる挙動（いわゆるハルシネーション）を実感した。
- 表示できたトークン数（入力 / 出力）：
  `response.usage_metadata` から取得。例えば「LoRAとは何ですか？」では 入力 7 トークン / 出力 611 トークン。日本語の長い説明は出力トークンが数百〜600以上になることが多かった。

## 宿題

- 取り組んだレベル：発展
- やったこと：
  `gemini-3.5-flash-lite`（既定モデル）と `gemini-3.5-flash`（`AIE_MODEL` で切り替え）の2モデルに対し、「LoRAとは何ですか？」（一般的な質問）と「AIE2026の講座の宿題にある『3レベル』とは何ですか？」（講座固有の質問）をそれぞれ投げ、応答時間と入出力トークン数を計測した。さらに `gemini-3.5-flash-lite` に対して間隔を空けずに8回連続でリクエストを送り、無料枠のレート制限（429）に引っかかるかを確認した。
- 結果：

  | モデル | 質問 | 応答時間[s] | 入力トークン | 出力トークン |
  |---|---|---:|---:|---:|
  | gemini-3.5-flash-lite | LoRAとは何ですか？ | 3.09 | 7 | 681 |
  | gemini-3.5-flash-lite | 宿題の3レベルとは？ | 2.99 | 21 | 673 |
  | gemini-3.5-flash | LoRAとは何ですか？ | 10.60 | 7 | 647 |
  | gemini-3.5-flash | 宿題の3レベルとは？ | 11.74 | 21 | 646 |

  出力トークン数はモデル間で大差なかった（650〜680程度）が、応答時間は `gemini-3.5-flash` が `gemini-3.5-flash-lite` のおよそ3〜4倍かかった。8回連続リクエスト（`gemini-3.5-flash-lite`、間隔なし）では429エラーは発生せず、全て0.4〜1.3秒程度で成功した。
- 気づき・疑問：
  - 既定モデルが `gemini-3.5-flash-lite` に設定されているのは、速度だけでなく無料枠のレート制限の緩さも理由になっていそうだと実感できた（`data/glossary.json` の `default-model` の説明とも一致する）。
  - 今回の短時間・少数回のテストでは429に遭遇しなかったが、`rate-limit` の用語集の説明にある通り、エージェント化して1質問あたりの呼び出し回数が増えると（第3回以降）上限に達しやすくなりそうで、継続的に使う場合は呼び出し頻度やリトライ戦略を考える必要があると感じた。
  - `-lite` ではないモデルの方が応答が遅いのは意外だった。精度と速度のトレードオフが用途（演習用の軽い質問 vs. 本番品質が必要なタスク）でどう効いてくるのか、今後の回で確認したい。
- 使ったモデル：`gemini-3.5-flash-lite`（既定）、`gemini-3.5-flash`（比較用、`AIE_MODEL` 環境変数で切り替え）

### 追加で取り組んだ内容（実装レベル）

発展レベルの提出後、興味があったので実装レベルにも追加で取り組んだ。

- やったこと：
  `app/ask.py` を改修し、`client.chats.create()` で作ったチャットセッション（`send_message`）を使うことで、最初の質問のあとは入力待ちになり、会話履歴を保ったまま続けて質問できるようにした（空行または Ctrl-D で終了）。
- 結果：
  以下のように3回続けて質問したところ、3回目の「私はどの街の天気について質問している？」に対して、1回目で聞いた「アムステルダム」を正しく答えられた。質問のたびに入力トークン数が増えていく（11 → 72 → 121）のも確認でき、裏側で過去のやり取り全体を毎回APIに送り直していることが分かる。

  ```
  $ uv run python -m app.ask "明日のアムステルダムの天気は？"
  [質問] 明日のアムステルダムの天気は？
  [トークン数] 入力: 11 / 出力: 54
  申し訳ありませんが、私はリアルタイムのインターネット情報にアクセスできないため、
  明日のアムステルダムの天気を直接お伝えすることができません。（以下略）

  [次の質問] あさっては？
  [トークン数] 入力: 72 / 出力: 38
  あさっての天気についても、明日と同様にリアルタイムの情報を確認することができません。（以下略）

  [次の質問] 私はどの街の天気について質問している？
  [トークン数] 入力: 121 / 出力: 39
  あなたが質問している街は「アムステルダム（Amsterdam）」です。
  最初に「明日のアムステルダムの天気は？」と尋ねていらっしゃいましたね。
  ```
- 使ったモデル：`gemini-3.5-flash-lite`
- 気づき・疑問：
  会話を続けるたびに、これまでの会話履歴全体を毎回APIに送り直しているため、ターンを重ねるごとに入力トークン数が線形に増えていく（累積の処理コストで見るとO(n²)）。本番で長い会話やRAGのような大きな固定コンテキストを扱う場合は、同じ内容を毎回送って再計算させるのは無駄が大きい。Gemini APIには **Context Caching**（`client.caches`）という、長い共通プレフィックスをキャッシュして再計算・再課金を抑える仕組みがあり、こうした場面で有効そう。ただし最小トークン数の制約があり、今回のような数百トークン規模の会話では使うメリットが小さいと思われる。
