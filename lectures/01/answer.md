### やったこと

**基礎**
- `app/ask.py` に `--temperature` オプションを追加し、`types.GenerateContentConfig(temperature=...)` で temperature を渡せるようにした
- 同じ質問「LoRAとは何ですか？」を temperature 0 と 2 でそれぞれ3回ずつ実行し、回答を比較した
- `.env` から APIキーを読み込むため `python-dotenv` を追加した（`.env` は `.gitignore` 対象でコミットしていない）

**実装**
- `--chat` フラグ（`argparse` の `store_true`）を追加し、付けたときだけ会話モードに入るようにした。付けない場合は従来どおり1回だけ質問する
- 会話モードでは `exit` と入力するまで質問を受け付け、会話履歴を保持して毎回APIに送る
- 設計で考えたこと
  - **履歴の置き場所**：履歴リストはループの外で用意した。中に置くと毎周空で初期化され、前の会話が消えるため
  - **送るもの**：`generate_content` は会話を覚えないので、「これまでの履歴＋今回の質問」を `types.Content`（`role` と `parts`）のリストとして毎回すべて送る
  - **エラー時の扱い（成功したときだけ履歴に足す）**：送信用のリストは `history + [今回の質問]` で新しく作り、本物の履歴は触らない。APIが成功したときだけ、質問（user）と回答（model）をまとめて履歴に足す。失敗した場合は履歴に何も足さず、エラーメッセージを表示して次の入力に戻る。レート制限などでエラーが起きても、履歴が「答えのない質問」や「前回の回答の使い回し」で壊れないようにするため
  - クライアントは毎回同じなのでループの外で1回だけ作り、APIを呼ぶ部分だけを `try` / `except errors.APIError` で囲んだ

### 気づき・疑問

- temperature 0 は「ランダムさを最小にする」設定であって、「毎回同じ出力」を保証するものではなかった。GPUの並列計算やサーバー側のバッチ処理によるわずかな差が、1トークンずれるとその後の文章全体に広がるためだと考えられる。
- LLMのAPIは会話を覚えていない（ステートレス）。「覚えている」ように見えるのは、過去のやりとりを毎回すべて送っているから。そのため会話が長くなるほど、1回あたりに送る入力トークン数が増えていく。無料枠のレート制限やコストとの関係が気になったので、次は発展レベルで計測してみたい。
- Gemini APIのドキュメントには、今回使った `generate_content`（履歴を自分で送る方式）とは別に、サーバー側で会話履歴を管理し前回のIDでつなぐ Interactions API もあった。自分で履歴を持つ方式と、サーバーに持たせる方式のトレードオフ（トークン数・制御のしやすさ・データの置き場所）を今後調べたい。a
