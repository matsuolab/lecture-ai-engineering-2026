## 演習

- 第1回（素のLLM）とエージェントの回答の違い：
  - 同じ「宿題の3レベル」の質問に、エージェントは「基礎（講義内容の確認）・実装（自分でコードを書く）・発展（調査や試行）」「どれか1つで完了」「原則として採点しない」と、用語集どおりに答えた。第1回の app.ask は9回とも「初級・中級・上級」の難易度として説明していた。
  - ただし追加で「完全に動かなくてもチャレンジすれば提出とみなされるか」と聞くと、`--trace` に tool call が1つもなく（requests=1）、用語集を調べずに「その通りです」「試行錯誤した形跡があれば認められます」と断定した。用語集にこの記述はない。INSTRUCTIONS の「必ず search_glossary で確認」「推測で断定しない」は、守られないことがある。
- `--trace` で見えたツール呼び出し（ツール名と引数）：
  - 「LoRAとQLoRAの違いは？」：`search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})`。docstring の「用語を1つだけ入れる」どおり、1語ずつ2回検索した。
  - 「第2回の内容から確認問題を1問出して」：`make_quiz({'lecture': 2})`（3回実行して3回とも呼ばれた）。
- 1つの質問での LLM 呼び出し回数（`requests`）：
  - ツールを使った質問は requests=2（1回目で検索を依頼、2回目で結果を見て回答）。入力トークンは 925〜1196。
  - ツールを使わなかった質問は requests=1、入力トークン 339。呼ぶたびに指示・ツール説明・会話・結果を送り直すので、トークンが増える。
- 追加したツールと、docstring に書いた説明：
  - `make_quiz(lecture: int) -> str`：用語集から指定の回の用語を `random.choice` で1つ選び、`{"question": "「○○」の意味は？", "answer": 定義}` を返す。該当する用語がない回（第0回など）はメッセージを返す。
  - docstring：「指定した回の用語から確認問題を1問作って返す。『第2回の確認問題を出して』『第3回の復習クイズがほしい』のように、確認問題やクイズを求められたときに使う」
  - 気づき：モデルは答えを表示せず「考えてみてください」と書いた。INSTRUCTIONS の「宿題の答えそのものは書かない」をクイズにも当てはめたと思われる。app.agent は1回で終わるので、続けてヒントや答えを聞くことはできない。問題文もツールの返した文から言い換えていた。

## 宿題

- 取り組んだレベル：発展 (b)
- やったこと：
  - Codespaces に Pi（`@earendil-works/pi-coding-agent` 1.5.0）を npm で入れ、空のフォルダ `~/pi-test` で起動した（宿題のリポジトリを書き換えられないようにするため）。
  - `/model` で `gemini-3.5-flash-lite` を選び、「このフォルダには何がありますか」と質問した。
  - Pi の会話の記録ファイル（`~/.pi/agent/sessions/` の `.jsonl`）から、実際にモデルへ送られたシステムプロンプトとツールの説明を Python で取り出し、`lectures/03/pi_system_prompt.md` に保存した。GitHub の `system-prompt.ts` も読み、どう組み立てているかを確かめた。
  - 演習のエージェントの `INSTRUCTIONS`（6行）と比べた。
- 結果：
  - Pi は確認を求めずに `ls -F` を実行し、「フォルダ内は空のようです」と答えた。rules の「ls・rg・find などのファイル操作は bash で行う」のとおりだった。
  - 最初に `gemini-3.1-pro-preview` を選ぶと、無料枠の「1分あたりの入力トークン数」の上限で 429 エラーになった（retryDelay は約21時間）。flash-lite に変えると動いた。Pi は毎回長い指示とツールの説明を送るので、入力トークンが多い。
  - Pi のシステムプロンプトは5つの部品でできていた：preamble（役割）、tools（read・bash・edit・write の一覧）、rules（8つのルール）、docs（Pi 自身の説明書の場所）、cwd（今のフォルダ）。
  - 比べた結果：

    | 観点 | 自分の INSTRUCTIONS | Pi |
    |---|---|---|
    | 役割 | AIE2026 の学習支援（専用） | コーディングの手伝い（汎用） |
    | ツールについて | いつ使うか（答える前に必ず search_glossary） | どう使うか（cat ではなく read、部分変更は edit） |
    | 正確さ | 用語集にないことは推測で断定しない | 書かれていない |
    | 答え方 | 最後に関係する回／宿題の答えは書かない | 簡潔に／ファイルの場所を示す |
    | 環境の情報 | なし | 今のフォルダ、説明書の場所、PI_ 環境変数 |
    | 安全・確認 | なし | なし |
    | 作られ方 | 1つの文字列を手で書いた | ツールごとのルールをプログラムが組み立てる |

- 気づき・疑問：
  - 自分のエージェントは「何を根拠に答えるか」、Pi は「道具をどう使うか」が中心だった。講座専用か、何でも頼まれる汎用かの違いだと思う。
  - Pi の指示には「危ない操作の前に確認する」が書かれていない。安全はプロンプトではなく、Codespaces という隔離された環境で守る前提になっている。演習で「必ず search_glossary で確認する」が破られたことからも、プロンプトに書くだけでは保証にならないと感じた。
  - Pi はツールが自分の使い方のルールを持ち寄る作りなので、ツールを外すとルールも消える。演習では make_quiz を足しても、INSTRUCTIONS は別に直す必要がある。
  - Pi はツールの説明に「2000行か 50KB で切り詰める」という制限まで書いている。自分の search_glossary は最大3件しか返さないが、docstring に書いていない。書いておけば、モデルが「ほかにも候補があるかもしれない」と判断できるかもしれない。
  - 疑問：Pi のルールは「Use 〜」と言い切る書き方で、自分の指示は「必ず〜する」。どちらの書き方のほうが守られやすいのか。
