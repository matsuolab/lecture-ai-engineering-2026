## 宿題

- 取り組んだレベル：発展
- やったこと：SWE-bench Verified を選び、データセットの問題を3件読み、元論文と公式の紹介資料で作成・検証方法を調べた。問題文の全文は転載せず要約した
  - [astropy__astropy-12907](https://github.com/astropy/astropy/issues/12907)：複合モデルを入れ子にしたとき、モデル間の独立性を示す分離行列が誤る問題。モデルの合成構造を追い、期待する行列と実装を照らし合わせる必要があり、単純なコード補完より難しい
  - [astropy__astropy-13033](https://github.com/astropy/astropy/issues/13033)：時系列データから必須列を削除した際、例外メッセージが実際の不足列を正しく示さない問題。必須列の判定とエラーメッセージの組み立てを追う必要がある
  - [astropy__astropy-13236](https://github.com/astropy/astropy/issues/13236)：構造化 NumPy 配列をテーブル列に追加するときの自動変換を見直す提案。既存の互換性を考慮しながら変換の振る舞いを変更し、通常配列やマスク付き配列のテストを整える点が難しい
- 結果：
  - データセット名・規模：[SWE-bench Verified](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified)。GitHub の実際の issue とコードベースを入力に、修正パッチを作るベンチマークで、Verified は人の開発者が解決可能性を確認した500件
  - 作成・検証：元の SWE-bench 論文の著者は7人。12の Python リポジトリから issue と、それを解決するマージ済み PR を集め、テスト変更のある候補を抽出。PR のテストを修正前後のコードで実行し、失敗から成功に変わるテストがあり、環境構築・実行に問題がない課題を残して、2,294件を作成した。Verified の検証では93人のソフトウェア開発者が参加し、各課題を3人が確認・解決を試み、問題が実際に解けるかを検証して500件に絞った
  - 採点：モデルが出したパッチを対象コードに適用し、課題に対応する失敗→成功テストと既存機能を確認するテストを実行する。テストを通過した課題の割合で評価し、LLM に回答の良し悪しを採点させる方式ではない
  - 今日の評価セットとの違い：今日のセットは講師1人が用意した質問・回答10件を人とLLMが複数基準で判定し、判定の一致率や要確認項目を見る。SWE-bench Verified は500件を複数の開発者が実際に検証し、コード修正をテスト実行で採点する。作問者数・規模・検証者数が大きく異なり、評価対象も回答品質ではなくリポジトリ上での修正能力である
- 気づき・疑問：実際の issue を使うことで現実的な課題になる一方、問題文だけでなくテストが本当に意図した不具合を検出するかも重要になる。今日の演習と同様、採点方法と検証者が何を確認したかを把握しないまま、ベンチマークのスコアだけを信頼するのは危険だと感じた
