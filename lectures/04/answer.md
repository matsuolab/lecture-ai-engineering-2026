## 宿題

- 取り組んだレベル：発展
- やったこと：
  - SWE-bench Verified を選んだ（https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified）
  - Hugging Face の Data Studio で問題を3件読み、problem_statement（報告文）と test_patch（採点用テスト）を見比べた
  - 作成と検証の手順を、OpenAI の公式ブログ2本と、検証者向けの指示書（PDF）で調べた
    - Introducing SWE-bench Verified（2024/8/13）
    - Why SWE-bench Verified no longer measures frontier coding capabilities（2026/2/23）
  - OpenAI が公開している検証者の回答データ（1,699件×3人分）で、読んだ3件の見積もりと理由を確認した
- 結果：
  - 読んだ問題（要約）。3件とも要望の内容は理解できたが、自分ではコードを修正できない
    - django__django-11179（見積もり15分未満、3人一致）：レコードを削除してもIDが残る不具合の修正。報告文に該当ファイルと行番号がある。LLMにとっては、見えないテストに通り、他の機能を壊さないことが必要
    - django__django-11239（見積もり15分未満、3人一致）：DB管理コマンドに証明書の設定を引き継がせる機能追加。実現方法は報告文にないが、テストは4つの環境変数を完全一致で確認していた
    - pydata__xarray-3993（見積もり1〜4時間、2対1の多数決）：積分機能の項目名が1か所だけ違うので統一する。移行期間の要否は報告文で疑問形のままだが、テストは古い名前での警告（FutureWarning）を必須としていた
  - 作成と検証の手順（出典：OpenAI ブログ 2024/8、検証者向け指示書）
    - 問題の出どころ：12のオープンソースPythonリポジトリの、解決済みの GitHub issue。ベンチマーク用の作問ではなく、実際の利用者の報告
    - 検証者：Python 経験のある開発者93人。事前に導入テストに合格した人のみ
    - 手順：無作為に選んだ1,699件を、各件3人が独立に確認。「問題文があいまいでないか」「テストが正しい解答を落とさないか」を4段階で評価し、3人のうち1人でも問題ありとした件は除外
    - 見積もり時間：実測ではなく、正解の修正とテストを見たうえで4区分から選ぶ主観的な見積もり。3人分は多数決（1,591件）か中央値（108件）でまとめられていた（出典：公開の回答データ）
    - 落とした割合：68.3%。残りから500件を選定
    - 採点：コードの実行。修正前は失敗し修正後に通るテストと、前後とも通るテストの両方に通れば合格。テストは解く側に見せない
    - その後（出典：OpenAI ブログ 2026/2）：モデルが安定して解けなかった138件を各件6人以上で見直したところ、59.4%にテストか問題文の不備があり、OpenAI はスコアの報告をやめた
  - 今日の評価セットとの違い（演習 → SWE-bench Verified）
    - 件数：10件 → 500件
    - 問題の出どころ：講師が作成 → 実際の GitHub issue
    - 検証の人数：講師1人が作成し受講生1人がラベル付け → 93人、各件3人が独立に確認
    - 落とした件数：なし → 1,699件の68.3%を除外
    - 採点の方法：人とLLM（4基準）、コード（1基準） → コードの実行（テスト）のみ
    - 判定の形：基準ごとに T / F / unsure → 合格か不合格
- 気づき・疑問：
  - 93人が3人ずつ確認して約7割を落としても、後の見直しで不備が見つかっている。講義の「完璧な評価はない」を数字で確認できた
  - 読んだ3件のうち2件で、報告文に書かれていないことをテストが求めていた（環境変数での受け渡し、移行期間の警告）。検証者の回答を見ると、同じ点を指摘した人がいたが、「落ちるのは変わった解答だけ」と判断して残していた。何を「変わった解答」と見るかは人の判断で、ここにも主観が入っている
  - 報告者が「些細な不満」と書いた問題（xarray-3993）の見積もりは、検証者3人で割れていた（1〜4時間が2人、15分〜1時間が1人）。見積もり時間は1人の判断では揺れる値だと分かった
  - 検証者向けの指示書は、段階ごとに実例を付け、理由を文章で書かせ、自信の度合いも答えさせていた。演習の rubric.md と同じ考え方だった
  - 演習には unsure（要確認）があり人が見る仕組みだが、SWE-bench Verified の採点はテストの合否だけで、あいまいな件を人に回す仕組みは採点側にない
  - 疑問：人が「変わった解答」と見なした方法を、LLMは普通に選ぶことがあるのではないか
