## 宿題

- 取り組んだレベル：発展
- やったこと：フロンティアモデルの評価ベンチマークとして **SWE-bench Verified** を選び、Hugging Face の Dataset Viewer（`princeton-nlp/SWE-bench_Verified`）で問題を 3 件読み、作成・検証の手順を OpenAI の公式ページ「Introducing SWE-bench Verified」（2024-08-13 公開、2025-02 更新）で調べた
- データセットとURL：
  - データセット：https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
  - 解説ページ：https://openai.com/index/introducing-swe-bench-verified/
- 読んだ問題の要約（3 件、全文は貼らず要約）：
  - `astropy__astropy-12907`：ネストした CompoundModel で `separability_matrix` が分離可能性を正しく計算しないという、実際の GitHub issue。再現コード付きで期待する出力が示されている
  - `astropy__astropy-13033`：TimeSeries で必須カラムのチェックに失敗したときに、誤解を招く例外が出るという報告
  - `astropy__astropy-13236`：structured column が自動で NdarrayMixin に変換される挙動をやめるべきでは、という機能変更の提案
  - 共通点として、いずれも「実際にマージされた PR に紐づく GitHub issue 文」が問題文で、正解はテスト（FAIL_TO_PASS / PASS_TO_PASS）で機械的に採点される。自分なら issue 文から原因を推測して修正箇所を当てるところまでは可能だが、リポジトリ全体を読み、既存機能を壊さないパッチを書き、非公開のテストを通すのは人間でも数十分〜数時間かかる規模感だった。LLM が解く場合、問題文に明示されていないテスト仕様（例：エラーメッセージの文言）まで要求されると、そもそも解けるかどうか以前に「問題が公正か」が問われる点が難しそうだった
- 作成の人数と手順：Python 経験のあるソフトウェア開発者 93 人が参加。元の SWE-bench テストセットからランダムに 1,699 件を選び、onboarding テストに合格したアノテーターが 1 件ずつチェックした。**各サンプルは別々のアノテーター 3 人がラベル付け**し、アンサンブルとして 3 人中最大の重大度ラベルを採用（1 人でも「深刻」と付ければ除外に近い慎重な合流）。判定項目は「issue 文の記述が不十分（underspecified）ではないか」「FAIL_TO_PASS テストが正当な解を弾いていないか」の 2 軸で、重大度 0〜3 の 4 段階（2,3 は除外対象）。補足として所要時間の見積もりも取り、難易度スライス（15 分未満の easy が 196 件、1 時間超の hard が 45 件）を作った。このフィルタリングの結果、500 件が SWE-bench Verified として残った。採点自体は人ではなく、Docker 化された評価ハーネス上のテスト実行による自動判定
- 今日の評価セットとの違い：
  - 規模と作成人が桁違い：今日のセットは 10 件・講師 1 人が作成、SWE-bench Verified は実際の GitHub issue から機械収集した母集団を、93 人が 1 件 3 名で検証して 1,699 → 500 件に絞っている
  - 「作る人」と「検証する人」の分離の度合い：今日のセットは作成者＝検証者だが、SWE-bench Verified は issue 執筆者（OSS 利用者）・PR 作成者・スクリーニングのアノテーターの 3 者が分離しており、onboarding テストと複数人ラベルの合流で検証側の品質も担保している
  - 採点方法：今日は T/F の人＋LLM 判定（うち 1 基準だけコード判定）だが、SWE-bench はコンテナ内テスト実行による全自動の二値判定。その分「問題文とテストの整合性」を検証の主対象にしている点が、LLM 採点器の rubric 設計を検証対象にした今日の演習と対照的だった
  - 共通しているのは「採点を信じられる根拠を先に作る」発想で、今日の unsure 切り分けに相当する役割が、あちらでは 4 段階の重大度ラベルと 3 人合議に相当していた
- 気づき・疑問：フロンティアの数字の裏には、検証に投じられた膨大な人件費があることが分かった。「ベンチマークの点が上がった」は「モデルが賢くなった」だけでなく「そのベンチマークが公正に測れるように整備された」結果でもあり、評価セットの品質保証（何人が・どう検証したか）こそが数字の信頼性を決める、という今日の講義の内容が実例で確認できた
