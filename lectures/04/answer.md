## 演習

- 基準別の一致率（直す前）：根拠 8/9、範囲 10/10、ヒント 10/10、分かりやすさ 9/10、回の表示 10/10（総合 9/9、自動判定できた 9/10 件 = coverage 90%）
- 要確認の件数（直す前）：1件（#05 の根拠。用語集にない「RAG」について、「用語集にはない」と伝えたうえで一般的な説明をした回答）
- 直した基準と、書き足した方針：根拠。「用語集にない語は、『用語集にはない』と伝えても、一般的な説明を加えた時点で推測での断定とみなす（fail）」と書き足し、「まだ決めていないこと」からこの論点を消した。理由：用語集にない余計な説明は、利用者の混乱を招くので、不合格にした
- 基準別の一致率と要確認の件数（直した後）：同じ設定で2回採点した。根拠は 7/9 と 8/9、範囲・ヒント・分かりやすさ・回の表示はどちらも 10/10（総合 9/9、coverage 90%）。要確認は2回とも1件のまま（#05 の根拠がまた unsure）。不一致は、1回目が #06 と #08 の根拠、2回目が #08 の根拠（どれも LLM の過検出）。方針を書き足した後の採点は合わせて4回で、LLM は #05 の根拠を pass が1回、unsure が3回とし、一度も fail にしなかった
- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：#05 の根拠だけ（自分は fail、講師は pass。基準別の一致は根拠 9/10、ほかは 10/10）。STEP 3 で「一般的な説明を加えたら推測での断定」という方針にしたため。なお、最初のラベル付けでは画面の初期値（合格）のまま保存した項目が多く、LLM との不一致8件のうち7件（#01 ヒント、#02・#07・#09 回の表示、#04 分かりやすさ、#06 ヒント、#10 根拠）は講師のラベルとも違っていた。基準と参照を読み直してラベルを直し、「直す前」を採点し直した。「迷った」を付けたのは、自分は #06、講師は #04・#05・#07 で、迷う項目は人によって違った。#06 で迷ったのは、回答に載っているコードが、宿題の答えそのものにも見えたため
- 気づき・疑問：
  - 最初の採点の総合の一致率は 3/9 だったが、原因の多くは LLM ではなく、正解として扱う人のラベルの付け間違いだった。一致率が低いときは、人のラベルの側も疑う必要がある
  - rubric に方針を1行書き足しても、要確認は減らなかった。方針を書き足した後に unsure になった3回とも、LLM は理由として、評価セットの参照（期待するふるまい）にある「一般的な説明をするかどうかは、まだ決めていない」を挙げた。rubric と参照が食い違うと、LLM は参照のほうに従うことがある。方針を決めたら、rubric だけでなく参照の文も直す必要がありそうだ（今回は1か所だけ直すルールなので、試していない）
  - LLM は基準を混ぜることがあった。#08 の根拠は採点のたびに fail（過検出）で、理由の多くは「指示に従って用語集を出した」という範囲の話だった。#06 の根拠と分かりやすさでも、「完成したコードを書いた」というヒントの話を持ち込んだ。rubric に「基準は1つずつ独立に見る」とあっても防げなかった
  - 同じ rubric でも判定は揺れた。#06 の分かりやすさは、rubric を直す前の2回で pass と fail に分かれた。#06 の根拠も、方針を書き足した後の4回で pass と fail が2回ずつだった。temperature 0 でも、1回の採点の数字だけで判断するのは危ない
  - #07 は「関係する回：なし」が妥当な答えだが、コードの判定（最後の行に「第N回」があるか）では不合格になる。コードの判定は揺れないが、規則が硬い

## 宿題

- 取り組んだレベル：発展
- やったこと：SWE-bench Verified（https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified ）を調べた。難易度の区分が違う問題を4件読み、作り方を OpenAI の記事（2024年8月の公開時と、2026年2月の報告停止時）で確かめた。
- 読んだ問題の要約：
  - 1件目（psf__requests-1142、15分未満）：HTTP ライブラリで、GET リクエストにも Content-Length ヘッダーが自動で付き、一部のサイトがエラーを返すという報告。何が困るかは分かったが、どこを直すかはコードを読めないので自分には分からない。LLM には易しそう。ただし採点のテストは HEAD でもヘッダーが付かないことを確かめていて、問題文は HEAD に触れていない。
  - 2件目（scikit-learn__scikit-learn-12682、15分〜1時間）：機械学習ライブラリで、内部のモデルの反復回数を利用者が指定できないという報告。問題文は「指定できるようにすべき」と書くだけだが、テストは transform_max_iter という引数名を要求する。LLM には、ライブラリの命名の習慣から名前を当てることが難しさになりそう。
  - 3件目（django__django-13212、1〜4時間）：Web フレームワークの入力チェックが、エラー文に入力値を埋め込めるようにしたいという要望。仕様ははっきりしているが、多くの入力チェックを漏れなく直す必要がある。議論では「本当に役立つか」という疑問も出ていて、仕様を決めること自体に人の判断が入っている。
  - 4件目（sympy__sympy-13878、4時間超）：数式処理ライブラリで、12種類の確率分布の累積分布関数を公式で持たせたいという要望。分布ごとの公式を知らないと書けないので、自分には解けない。LLM には、数学の知識と、12種類を正しく書き分ける量が難しさになりそう。一方、新しく合格が必要なテストは arcsin 分布の1本だけだった。
- 作成の人数と手順：
  - 元の SWE-bench（2023年）は、12の Python リポジトリの解決済みの issue と PR から2,294件を作った。問題文は issue の原文で、正解は実際に直した PR の修正とテスト。
  - Verified（2024年8月）は、OpenAI が Python の経験が豊富な開発者93人に依頼して、無作為に選んだ1,699件を確認した。参加者は、OpenAI のエンジニアがラベルを付けた50件で事前テストを受け、合格する必要があった。1件につき別々の3人が、「問題文があいまいか」「テストが正しい解答を落とさないか」を0〜3の4段階で評価し、3人のうち最も厳しい評価を採用した。2以上の件と、ほかの重大な問題を指摘された件を除いた結果、68.3%が除外された。残りから、時間のかかる問題をできるだけ含めて500件を選んだ。
  - 採点は、AI の修正を当てたあとに、修正前は失敗して修正後に通るはずのテスト（FAIL_TO_PASS）と、前後どちらでも通るはずのテスト（PASS_TO_PASS）をすべて実行して判定する。テストは AI に見せない。
  - その後、2026年2月に OpenAI は Verified の報告をやめた。o3 が64回実行しても解けなかった138件を、1件につき6人以上のエンジニアが見直したところ、59.4%でテストか問題文に重大な不備があった（実装の細部まで決めつける狭いテストが35.5%、問題文にない機能まで確かめる広いテストが18.8%）。また、試した最先端のモデルはどれも、一部の問題の正解の修正や問題文を再現できた（学習データへの混入）。
- 今日の評価セットとの違い：
  - 規模：今日は10件。Verified は500件（確認したのは1,699件）
  - 検証の人数：今日は講師1人が作り、受講生がそれぞれラベルを付けて LLM の判定と比べた。Verified は1件に3人、報告停止のときの見直しでは1件に6人以上
  - 採点の方法：今日は LLM が4つの基準を判定し、「回の表示」だけをコードで判定した。Verified はテストを実行して判定するので、採点に LLM を使わない。代わりに、テストそのものが問題文と合っているかを人が確かめる必要がある
- 気づき・疑問：
  - 演習では、LLM の採点を人のラベルと比べて、見逃し（LLM は合格、人は不合格）と過検出（その逆）を数えた。Verified の4段階の評価は、主に「正しい解答をテストが落とす」側、つまり過検出の側を見ていて、「不十分な解答でもテストを通ってしまう」側は自由記述の指摘で拾う形だった。読んだ4件目は、テストの一覧を見る限り、arcsin だけ直した修正でも合格になりうる（実際には試していない）。採点がコードでも LLM でも、両方の向きの誤りを確かめないと採点を信じられないと感じた。
  - 今日の10件も公開リポジトリにある。Verified が学習データへの混入で使えなくなったように、自分の評価セットを長く使うなら、公開する場所や、ときどき問題を入れ替えることも考える必要がある。
