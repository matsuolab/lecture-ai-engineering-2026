## 宿題

- 取り組んだレベル：発展
- やったこと：
  - データセット：SWE-bench Verified
    - データ：https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified （500 件。ログインなしで見られる）
    - 作成と検証の出典：OpenAI「Introducing SWE-bench Verified」（2024-08-13 公開、2025-02-24 更新） https://openai.com/index/introducing-swe-bench-verified/
  - Hugging Face の Data Studio で、先頭の 5 件（astropy＝天文学の Python ライブラリ）の問題文（`problem_statement`）を読んだ。英語の原文は AI に日本語で要約してもらい、画面と照らした
  - OpenAI の記事で、作った人数・検証の手順・採点の方法を調べた
- 結果：
  - 中身：実際の GitHub の issue（利用者が書いた不具合報告や要望）と、それを直した PR から作った課題。エージェントには issue の文章とコード一式だけを渡し、テストは見せない。問題文は AI が作ったものではなく、人が書いた文章そのまま
  - 読んだ問題の要約（全文は貼らない）
    - astropy-12907（15分〜1時間）：入れ子にしたモデルで、入力と出力が独立かどうかを表す行列が間違う
    - astropy-13033（15分〜1時間）：時刻つきの表で必須の列を消すと、「最初の列は time のはず」という的外れなエラーが出る。足りない列が分かるエラー文に直す
    - astropy-13236（15分〜1時間）：表に構造化配列を入れたとき、勝手に別の型へ変換するのをやめたいという提案
    - astropy-13398（1〜4時間）：地球に固定した座標系から地平座標へ、直接変換する機能の提案
    - astropy-13453（15分〜1時間）：表を HTML で書き出すとき、指定した数値の書式が無視される
  - 自分なら解けるか：解けない。何を問うているかは要約を読めばおおよそ分かるものもあるが、どこのコードをどう直すのが正しいかは、まったく判断できなかった
  - LLM が解くとしたら難しい点：大きなコードの中から直す場所を自分で探すこと。採点に使うテストを見ないまま、テストが求める形に合わせること（記事の例では、テストが警告の文言を一字一句同じにすることを求めていて、その文言は問題文に書かれていなかった）
  - 作成の人数と手順（OpenAI の記事より）
    - Python の経験があるプロの開発者 93 人が検査した。参加するには、OpenAI のエンジニアが先に付けた 50 件で作った試験に合格する必要があった
    - 元のテストセットから 1,699 件をランダムに選び、1 件を別々の 3 人が検査した
    - 見る点は「問題文は十分か」「テストは正しい解答を落とさないか」の 2 つで、それぞれ 0〜3 の 4 段階。3 人のうち一番厳しい判定を採り、2 以上（＝1 人でも問題を指摘したもの）は除外した
    - 問題文が不十分 38.3%、テストが不適切 61.1%、全体で 68.3% を除外した。残りから 500 件を選んだ
    - 難しさ（直すのにかかる時間）も見積もったが、絞り込みには使っていない
  - 採点の方法：直したコードを当てて、FAIL_TO_PASS（直す前は失敗し、直した後に通るテスト）と PASS_TO_PASS（前後どちらでも通るテスト）が両方通れば解決。テストで機械的に決まり、人も LLM も採点しない
  - 今日の評価セットとの違い

    |---|---|---|
    | 件数 | 10 件 | 500 件（1,699 件を検査して絞った） |
    | 問題を作った人 | 講師 1 人（回答は第3回のエージェント） | 実際の開発で人が書いた issue と修正 |
    | 検証 | 講師 1 人のラベル | 試験に通った開発者が 1 件を 3 人で検査 |

- 気づき・疑問：
  - 問題を読んでも、何が正しいか自分には判断できなかった。演習の 10 件は、参照を見れば自分でもラベルを付けられたが、SWE-bench は専門家でないと「問題が正しく作られているか」さえ判断できない。だから 93 人の開発者を集め、試験で選び、1 件を 3 人で見る必要があるのだと思った
  - 演習では、曖昧なものを unsure にして人が方針を決めた。SWE-bench Verified は、曖昧なものを決めずに捨てている。7 割近くを捨てて残すのは、大きな元データがあるからできることで、10 件の評価セットでは同じことはできない
  - テストで機械的に採点できるのは、コードの課題だから。演習の「根拠」や「分かりやすさ」のような基準は、テストにできない。採点の方法は、何を評価するかで決まる
