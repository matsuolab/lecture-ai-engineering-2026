# 第4回 解答

## 演習

本提出は宿題の「発展」を対象とする。以下は公開データセットと一次資料を調査した結果である。演習の Gemini 採点は今回再実行していないため、人手ラベルとの一致率や基準変更前後の数値は記載しない。

## 宿題

- 取り組んだレベル：**発展**
- やったこと：SWE-bench Verified の問題文5件を読み、作成・検証の体制と採点方法を公式資料で調べ、講座の10件の評価セットと比較した。
- 調査日：2026年11月16日
- 実施範囲：問題文の読解と資料調査。問題の修正コードの実装、ベンチマークの実行、モデルのスコア測定は行っていない。発展課題ではコード作成は求められていない。[1]

### 1. 定義と主なポイント

SWE-bench は、実際の GitHub issue と修正前のリポジトリを与え、問題を解消するコード変更（パッチ）を生成させる評価である。Verified は、そのうち人が品質を確認した500件の部分集合である。[2–4]

重要なのは、難しい問題を集めるだけでは不十分であり、**問題文から要求が理解できることと、妥当な別解を採点基準が排除しないこと**も確認している点である。これは、講座で採点器の判定と参照ラベルを比較する目的に通じる。[1,2]

### 2. 実際に読んだ問題5件

公式配布データの `problem_statement` を確認した。全文は転載せず要約する。IDは issue 番号とは限らないため、データセットの `instance_id` として示す。[3]

| instance_id | 問われていること | 解く際の難しさ・着手の見通し（問題文に基づく考察） |
|---|---|---|
| `astropy__astropy-12907` | 入れ子にした複合モデルで、入出力の独立性を示す行列が、平坦に結合した場合と異なる結果になる問題。 | 再現例があり着手しやすいが、行列の結合処理を追い、入れ子でも依存関係を保存する修正が必要。行列の知識だけでは修正箇所までは分からない。 |
| `astropy__astropy-13033` | 時系列の必須列を削除した際、実際の欠落を説明しない紛らわしい例外が出る問題。 | 期待する挙動は比較的明確。ただし表示文だけを変えず、複数の必須列を扱う検証処理を確認する必要がある。 |
| `astropy__astropy-13236` | 構造化配列を表へ追加すると自動的に `NdarrayMixin` へ変換する挙動を見直す提案。 | 問題文に変更方針はあるが、警告を経た移行と最終的な変更を区別し、既存の入出力・互換性への影響を調べる必要がある。単純なバグ修正より仕様理解が重要。 |
| `django__django-10097` | URL検証で、ユーザー名・パスワード部に不適切な未エンコード文字を含むURLを受理する問題。 | 反例があるため再現しやすい。正規表現を修正する場合、正しいURLまで拒否しないことを境界例で確認する必要がある。 |
| `django__django-10554` | 和集合と並べ替えを使う QuerySet から派生したクエリの評価後、元のクエリの再評価が失敗する問題。 | 評価順序を含む再現手順を追い、クエリの複製や状態共有、生成SQLまで調べる必要がある。5件の中では、局所的な文言修正より広いコード理解が必要と考えた。 |

これらは問題文の読解に基づく難しさの見積もりであり、解けたという実測ではない。LLMにとっても、文章としてもっともらしい説明を出すだけでは足りず、修正箇所の特定と既存機能を保つ変更が必要になる。

### 3. 作成人数と作成・検証の手順

Verified は新たに500問を書き起こしたものではなく、既存の実務課題を選別したものである。品質確認には **Python経験のある開発者93人**が参加し、抽出した **1,699件**を**各3人が独立に確認**した。93人を元のissueすべての作問者数と解釈してはいけない。元の報告者・修正者を含めた総人数は、確認した資料からは確定できない。[2]

検証の流れは次のとおりである。[2]

1. 運営側が50件に高確信度のラベルを付け、参加者の導入テストと訓練に利用する。
2. 問題文の明確さと、テストが正当な修正を誤って不合格にしないかを0〜3の重大度で評価する。修正時間の見積もりと、その他の重大な問題も記録する。
3. 3人の重大度の最大値を採用する。主要基準が2以上、またはその他の重大な問題がある項目を除外する。多数決ではなく、問題の見落としを避ける保守的な集約である。
4. この過程で68.3%が除外された。残った全件をそのまま500件とするのではなく、難しい問題をできるだけ含め、残りを抽出して最終的な500件を構成する。

### 4. 採点方法と講座の評価セットとの比較

修正パッチを適用した後、修正前に失敗していたテストと、修正前から成功する既存テストの両方を通過することで解決を判定する。参照パッチとの文字列一致や、LLMによる回答文の採点ではない。公式の評価環境はDockerを用いる。[2,4]

| 比較項目 | 第4回の評価セット | SWE-bench Verified |
|---|---|---|
| 規模・由来 | 講師が準備した質問・回答10件。正常系とエッジケースを含み、一部に失敗を混ぜる | 実際のOSS課題から品質確認して選んだ500件 |
| 人の関与 | 講師の参照ラベルと受講者のラベルを比較 | 開発者93人が参加し、各問題を3人で品質確認 |
| 評価対象 | 既に生成された学習支援エージェントの回答 | issueに対して生成したコード変更 |
| 自動判定 | 4基準はLLM、末尾の回表示はコード | 修正・回帰テストの実行 |
| 曖昧さへの対応 | `unsure` を人の確認へ回し、基準を具体化 | 重大な曖昧さや不公平なテストを持つ問題を除外 |
| 得られる指標 | 基準別の一致率、総合一致率、自動判定できた割合 | 問題を解決した割合 |

講座の一致率は「採点器が参照ラベルと一致するか」、SWE-benchの解決率は「エージェントの変更がテストを通過するか」を表す。両者は評価対象も分母も異なるため、そのまま優劣比較できない。[1,2]

### 5. 気づき・疑問、制約

考察：チェックをコードにすると同じ条件で再実行しやすいが、テスト自体が要求とずれていれば正しい解を落とす。人が複数人で検証することは、そのずれを減らす工程であり、採点の妥当性を永久に保証するものではない。講座でも、一致率を上げるだけでなく、不一致の原因が回答・ラベル・基準のどこにあるかを確認する必要がある。

現在の位置づけにも注意が必要である。OpenAIは2026年2月23日の再監査で、選択した138件の59.4%に重大な問題を報告した。これは難問を中心に選んだ部分集合であり、500件全体の不良率へ一般化できない。訓練データへの混入も指摘されている。[5] なお、同記事でのSWE-Bench Proへの移行推奨も、同年7月8日の追加監査で撤回された。[6] したがって、ここではVerifiedを「現在も最良の評価」として推奨するのではなく、**評価データの構築と再検証を学ぶ事例**として扱う。

今回の5件は便宜的に選んだ例であり、全500件の代表性はない。また、読解のみなので、実際に必要な修正時間やモデルの解決能力は測っていない。

### 6. 用語

- ベンチマーク：共通の課題・採点方法でシステムを評価する枠組み。
- `FAIL_TO_PASS`：対象の修正前には失敗し、修正後に成功することを求めるテスト。
- `PASS_TO_PASS`：修正前後とも成功し、既存機能への悪影響を検出するテスト。
- 回帰：変更によって、それまで動作していた機能が壊れること。
- データ汚染：評価問題や解答が訓練データ等に含まれ、未知の課題を解く能力と区別しにくくなること。
