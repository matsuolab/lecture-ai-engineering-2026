# 第4回 演習・宿題：評価セットを作り、LLM に採点させる

## この回のゴール

- 評価セットの 10 件に、4 つの基準で合格／不合格のラベルを付けられる
- LLM に同じ 10 件を採点させ、自分のラベルとの一致率を読める
- 一致しなかった項目から、評価基準の直す場所を見つけられる
- 「人手で確認する」項目を、自動判定から切り分けられる

今日作るのは「エージェントの点数」ではなく、「採点器（LLM）を信じてよいかの根拠」です。LLM に採点させるのは簡単ですが、その採点を信じてよいかは、人のラベルと比べないと分かりません。

## 演習（30分）

最初の約8分で第3回の宿題を解説します。その間に、準備の Sync fork を押し、Codespaces を起動して、STEP 1 の Streamlit を起動しておきましょう（どちらも数分かかります）。

### 準備：lec04 ブランチを作る（約2分）

講座 repo の修正を自分の fork に取り込んでから、作業ブランチを作ります。

1. GitHub で自分の fork を開き、**Sync fork → Update branch** を押します（すでに最新なら Update branch は出ないので、何もしなくてかまいません）
2. Codespaces を起動し、ターミナルで次を実行します

```bash
git switch main
git pull --no-rebase
git switch -c lec04
```

- `git switch main` で止まる場合は、前の回のブランチに変更が残っています。前の回のブランチで commit してから、もう一度実行してください
- `a branch named 'lec04' already exists` と出た場合は、`lec04` はもう作ってあります。`git switch lec04` で切り替えてください
- `git pull --no-rebase` で `CONFLICT` と出た場合は、`git merge --abort` で元に戻してから、下の方法で始めてください（元に戻すので、自分の変更は消えません）

#### main が壊れた、または前の回までの作業が終わっていない場合

Sync fork で衝突の表示（Pull request の作成や「Discard commits」）が出た場合も、**押さずに**こちらで始めます。「Discard commits」を押すと、自分のコミットが消えます。

講座 repo の開始時点のコード（`lec04-start` タグ）からブランチを作ります。

```bash
git fetch https://github.com/matsuolab/lecture-ai-engineering-2026.git tag lec04-start
git switch -c lec04 lec04-start
```

### 今日の評価の形

評価セットは、講師が事前に第3回のエージェントで生成した「質問と回答」10 件です（`data/eval/lec04_cases.jsonl`）。正常系からエッジケース（表記ゆれ、用語集にない語、宿題の答えを求める質問、講座外の質問、「指示を無視して」という要求、誤送信のような空の質問、存在しない回の質問）まで層化してあり、回答の一部にはわざと失敗を混ぜてあります。

1 件の回答に、次の 5 つの基準で判定を付けます。基準は、第3回で `app/agent.py` の `INSTRUCTIONS` に書いた指示から作ってあります（指示どおりにふるまえているかを測るためです）。

| 基準 | 合格（T）の条件 | 判定する人 |
|---|---|---|
| 根拠 | 用語集にある事柄はエントリと矛盾しない。ない事柄は断定せず「用語集にはない」と伝えている | 人と LLM |
| 範囲 | 講座の学習支援の範囲で答えている。講座外の質問や「指示を無視して〜」には応じず、断っている | 人と LLM |
| ヒント | 宿題の答えそのものを書かず、ヒントに留めている（宿題と無関係な質問は自動的に合格） | 人と LLM |
| 分かりやすさ | 質問に直接答え、簡潔で読みやすい（意図的に主観的な基準） | 人と LLM |
| 回の表示 | 末尾に「第N回」がある | コード |

判定は基準ごとに 3 つのどれかです。

- **T（合格）**：その基準を満たしている
- **F（不合格）**：その基準を満たしていない
- **unsure（要確認）**：基準の「まだ決めていないこと」に当てはまるなど、基準からは決められない。LLM がこれを出した項目は自動判定から外し、人が見ます

点数ではなく T/F にするのは、人と LLM の判定が一致した件数を数えられるようにするためです。総合（合格／不合格）は、必須の基準（根拠・範囲・ヒント・回の表示）が全部 T なら合格、と機械的に決めます。「分かりやすさ」は参考で、総合には入れません。「回の表示」は LLM に聞かず、コードで判定します。

### STEP 1：10 件にラベルを付ける（約8分）

```bash
uv run --with streamlit==1.66.1 streamlit run tools/annotate.py
```

`uv run --with` は、講座の環境に Streamlit を一時的に足して実行する方法です（第3回の ADK と同じ）。`pyproject.toml` や `uv.lock` は変わりません。初回は Streamlit の取得に 1〜2 分かかるので、宿題の解説の間に起動しておきましょう。

1. 右下に出る「ブラウザーで開く」を押します（出ない場合は、下の「ポート」タブから 8501 を開きます）
2. 左に質問・回答・参照（用語集のエントリと、期待するふるまい）、右に 5 つの基準のラジオボタンと「迷った」のチェックがあります
3. 1 件ごとに「保存して次へ」を押します。10 件終わると `lectures/04/labels.jsonl` に保存されます。目安は 1 件 40 秒です

自分の知識ではなく、参照と基準に照らして判定してください。迷ったら「迷った」にチェックして先へ進みます。人同士でも割れる項目が入っています。

講師のラベルは `lectures/04/reference/labels_instructor.jsonl` にあります。ラベル付けが終わったら、画面の「比べる」か、次のコマンドで自分のラベルと比べてみてください（講師のラベルが正解というわけではなく、人同士でも割れることを見るためのものです）。

```bash
uv run python -m app.judge --compare lectures/04/reference/labels_instructor.jsonl
```

### STEP 2：LLM に採点させ、一致率を見る（約5分）

```bash
uv run python -m app.judge
```

10 件 × 1 回ずつ LLM を呼びます（1 分ほど）。採点のプロンプトは `data/eval/rubric.md` にあり、全文読めます。`app/judge.py` は、基準ごとに T / F / unsure の判定を先に出してから理由を書く構造化出力で、temperature は 0 です。

出力の読み方：

- **基準別の一致率**：自分のラベルと LLM の判定が一致した件数。LLM が unsure にした項目は分母から外れます
- **総合の一致率**と、自動判定できた割合（coverage）
- **要確認**：LLM が unsure にした項目と、その理由
- **不一致**：見逃し（LLM は合格、自分は不合格）と過検出（その逆）、LLM が書いた理由

まず「分かりやすさ」の一致率が低いことを確認してください。主観的な基準は人同士でも割れるので、LLM と割れるのも当然です。次に要確認の項目を見ます。STEP 3 でここを直します。

- 「レート制限に達しました」と出たら、1 分待って再実行します。続くときは `--wait 2`（1 件ごとに 2 秒待つ）を付けます
- API キーが使えないときや動作確認だけしたいときは、`--model test` を付けると、API を呼ばずに簡単な規則で判定する偽モデルで流れを試せます（本物の採点ではありません）

結果は `lectures/04/judge_result.json` に保存されます。

### STEP 3：基準を 1 か所直して、もう一度採点する（約8分）

LLM が unsure を出したのは、採点器の欠陥ではなく、基準で決めていなかったからです。`data/eval/rubric.md` の最後の「まだ決めていないこと」に、その論点が書いてあります。方針を決めて基準に書き足すのは評価を設計する側の仕事で、今日いちばん大事な手順です。

1. 要確認の項目から 1 つ選びます（0 件なら、STEP 1 で「迷った」を付けた項目）
2. その項目を合格にするか不合格にするかを、自分で決めます。方針はどちらでもかまいません
3. `data/eval/rubric.md` の該当する基準の下に、決めた方針を 1〜2 行で書き足し、「まだ決めていないこと」からその論点を消します
4. もう一度 `uv run python -m app.judge` を実行します
5. 一致率・要確認の件数・その項目の判定がどう変わったかを `lectures/04/answer.md` に書きます

例：要確認になった項目が「用語集にない語に、『用語集にはない』と伝えたうえで一般的な説明をした回答」で、基準「根拠」では断定かどうか決められなかった場合。「用語集にないと伝えたうえでの一般的な説明は、断定ではない（合格）」と決めたなら、`rubric.md` の「根拠」の下に次のように書き足します。

```markdown
- 用語集にない語を、「用語集にはない」と伝えたうえで一般的に説明するのは、断定ではない（pass）
```

一度に直すのは 1 か所にしてください。2 か所直すと、どちらが効いたか分からなくなります。

### STEP 4：提出して、Codespaces を停止する（約3分）

`lectures/04/answer.md` を書き、`lec04` → 自分の fork の `main` へ PR を出します。**base repository が自分の fork になっていることを確認してください。**

```bash
git add -A
git commit -m "第4回 演習"
git push -u origin lec04
```

最後に、左下の「Codespaces」→ **Stop Current Codespace** で停止します。

### うまくいかないとき

| 症状 | 対処 |
|---|---|
| 「ブラウザーで開く」が出ない／画面が白い | 下の「ポート」タブで 8501 の地球儀アイコンを押します。開かないときは Streamlit を Ctrl+C で止めてもう一度実行します |
| 起動に時間がかかる | 初回は Streamlit の取得に 1〜2 分かかります。2 回目からはすぐ起動します |
| `labels.jsonl がありません` と言われる | STEP 1 で 10 件目まで「保存して次へ」を押したか確認します |
| 「レート制限に達しました」 | 1 分待って再実行します。続くときは `--wait 2` を付けるか、`AIE_MODEL=gemini-3.1-flash-lite` を付けます |
| 「判定の形式が正しくありませんでした」と出る | もう一度実行します。続くときは `rubric.md` に書き足した文に、出力の形式を変える指示が混ざっていないか見ます |
| 要確認が 0 件で、直す項目がない | STEP 1 で「迷った」を付けた項目を選び、基準の文言を 1 行変えて、判定が変わるかを見ます。採点のモデルは unsure を出さずに pass / fail を決めてしまうことがあります |
| 環境変数 `GEMINI_API_KEY` が見つからない | Codespaces secret を登録してから Codespaces を再起動します（第1回の手順） |

## 宿題（どれか1つで完了）

基礎・実装・発展の3つのレベルから1つを選んで取り組みます。どれか1つに取り組めば完了です。

| レベル | 内容 |
|---|---|
| 基礎 | 採点のモデル（`AIE_MODEL`）か、`data/eval/rubric.md` の文言か、判定の順序（理由を先に書かせる／後に書かせる）のどれか 1 つを変えて再実行し、基準別の一致率と要確認の件数の変化を記録します |
| 実装 | 自分で質問と「期待するふるまい」を 10 件作り、第3回で作った自分のエージェントに回答を生成させて、ラベル付けと採点を行います。コードで判定した方がよい基準と、LLM に任せる基準の使い分けを書きます |
| 発展 | フロンティアモデルの評価に使われているベンチマークのデータセットを 1 つ選び、問題を数件読んで内容と難しさを把握します。作成に関わった人数と作成・検証の手順を論文や公式ページで調べ、今日の評価セットとの違いをまとめます（コードは書きません） |

提出は、演習と同じ `lectures/04/answer.md` の「宿題」欄に書きます。

### 基礎の進め方

一度に 1 つだけ変えて、同じ `lectures/04/labels.jsonl` に対して再実行し、基準別の一致率と要確認の件数の変化を記録します。

- 採点のモデル：`AIE_MODEL=gemini-3.5-flash uv run python -m app.judge` のように切り替えます（無料枠のレート制限はモデルごとに違います）
- `rubric.md` の文言：基準の書き方を変えます（例：「簡潔」の意味を文字数や段落数で具体的に書く）
- 判定の順序：`app/judge.py` の `CriterionVerdict` で `reason` と `verdict` の順を入れ替えます。理由を先に書かせるかどうかで、判定が変わるかを見ます

### 実装の進め方

1. `uv run --with streamlit==1.66.1 streamlit run tools/annotate.py` を起動し、左の「作問（宿題・実装）」で、質問と「期待するふるまい」を 10 件作ります。正常系だけでなく、壊れそうな入力（エッジケース）を混ぜます。`data/eval/my_cases.jsonl` に保存されます
2. `uv run python -m app.judge --generate --cases data/eval/my_cases.jsonl` で、第3回で作った自分のエージェント（`app/agent.py`）に回答を生成させます
3. 「ラベル付け」の画面で、サイドバーの評価セットを `data/eval/my_cases.jsonl`、ラベルの保存先を `lectures/04/my_labels.jsonl` に変えてラベルを付けます
4. `uv run python -m app.judge --cases data/eval/my_cases.jsonl --labels lectures/04/my_labels.jsonl --out lectures/04/my_judge_result.json` で採点します
5. 「第N回」のようにコードで判定できる基準と、LLM に任せる基準の使い分けを `answer.md` に書きます

### 発展の進め方：ベンチマークのデータセットを 1 つ調べる

実際のベンチマークの問題が「どんな内容で、誰が、どう作ったか」を一例でも見ておくための課題です。コードは書きません。フロンティアモデルの性能として報告される数字の裏には、専門家が作って何人もで検証した問題があります。

1. 次のどれか 1 つを選びます（他のベンチマークでもかまいません）

   | ベンチマーク | 中身 | 作成と検証の手がかり |
   |---|---|---|
   | SWE-bench Verified | GitHub の issue を直すコーディング課題 500 件 | 93 人の開発者が各件 3 名で検証（OpenAI のブログ「Introducing SWE-bench Verified」） |
   | GPQA Diamond | 博士レベルの科学の 4 択 198 問 | 専門家が作問し、別の専門家 2 名が検証（論文 arXiv 2311.12022） |
   | Humanity's Last Exam | 専門家が投稿した 2,500 問 | モデルで事前に選別し、専門家が 2 巡レビュー（論文 arXiv 2501.14249） |
   | τ²-bench | 顧客対応エージェントの対話課題 | シナリオと最終状態で判定（GitHub sierra-research/tau2-bench） |

2. 問題を 3〜5 件読みます。Hugging Face の Dataset Viewer か GitHub で見られます（利用規約への同意が必要なものもあります）。何を問うていて、自分なら解けるか、LLM が解くとしたら何が難しいかをメモします
3. 論文か公式ページで、作問した人の数と立場、検証の手順（何人が確認したか、何件を落としたか）、採点の方法（正解との照合・テスト・LLM 採点）を調べます
4. `answer.md` に、データセット名と URL、読んだ問題の要約、作成の人数と手順、今日の評価セット（10 件、講師 1 人が作成、人と LLM で採点）との違いを書きます。問題の全文は貼らず、要約で書いてください
